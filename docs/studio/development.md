# Development

## The crates

- `plugin-agy/`: the studio's plugin for agy (#43). `hooks.json` runs `plotkeeper-hook` for agy's six events through an inline wrapper that always exits 0 with empty stdout; `plotkeeper-hook` writes an agy event from any terminal, and drops every event from a process with `PLOTKEEPER_INTERNAL=1` (#323). `plotkeeper install` renders it with the path of `plotkeeper-hook` in the data folder's `bin/` and installs it with `agy plugin install`, which copies the folder ([install](plugin.md)).
- `plugin-codex/`: plotkeeper's entries for Codex's user-level hook file (#359). `hooks.json` runs `plotkeeper-hook --agent codex` on eight of Codex's events; `plotkeeper install` renders it with the data folder's `bin/` and adds its groups to `~/.codex/hooks.json` beside the user's own ([install](plugin.md)). `core/src/codex.rs` reads the lines.
- `plugin-cursor/`: plotkeeper's entries for Cursor's user-level hook file (#362). `hooks.json` runs `plotkeeper-hook --agent cursor` on seven of Cursor's events that wait on no answer; `plotkeeper install` renders it with the data folder's `bin/` and adds its entries to `~/.cursor/hooks.json` beside the user's own ([install](plugin.md)). `core/src/cursor.rs` reads the lines.
- `plugin-copilot/`: plotkeeper's plugin for Copilot, CLI and VS Code's agent (#361). `hooks.json` runs `plotkeeper-hook --agent copilot --event <name>` on seven of Copilot's camelCase events, whose payloads name no event; `plotkeeper install` renders it with the data folder's `bin/` and installs it with `copilot plugin install` ([install](plugin.md)). `core/src/copilot.rs` reads the lines, in either casing.
- `plugin/`: the Claude Code plugin, which `plotkeeper install` renders with the data folder's `bin/` and installs with `claude plugin install` ([install](plugin.md)). On thirteen hook events, `SubagentStart` and `SubagentStop` among them, it runs `plotkeeper-hook`. On the `PreToolUse` of `AskUserQuestion` and `ExitPlanMode`, on every `PermissionRequest`, and on the `PermissionDenied` and `PreToolUse` of Bash, it also runs `plotkeeper-answer`, synchronously.
- `hook/`: `plotkeeper-hook`, which appends each hook payload as one line to the event log, and the log's path; it also records each turn's and worker's trees and the worktree roots a call touched (`studio_touched_roots`), from the folders and paths the call names, the roots `git worktree list` gives and the roots it already knows; and `plotkeeper-answer`, the answer hook (danielrispler/Falinks#477, danielrispler/Falinks#478): while the studio watches the asking session, it waits up to 120 seconds for an answer from the card and returns it: a question's `answers`, a plan's approval or rejection, a permission's allow or deny. It logs that answer as a `StudioAnswer` line, which clears "needs you" for a plan or a permission at once. Otherwise it returns at once with no decision and the terminal asks. On a Bash `PermissionDenied` it leaves a request in `blocked/<session>/` and waits up to 600 seconds, while the window shows life whatever session it shows, for Allow (`retry: true`) or Decline; Allow also leaves a 30-minute one-time pass in `passes/<session>/`, which the retry's `PreToolUse` claims and its `PermissionRequest` spends.
  - Its files and trust boundary are in `hook/src/answer.rs`.
- `core/`: the studio core, plain Rust whose only I/O is reading the sessions' transcripts (`src/transcript.rs`, `.jsonl` files only), and `scrub`, which turns event log lines into test fixtures. At start the app takes the state its last start saved, `studio-state.json` beside the log, and replays only the log from where that state stopped, then feeds it each new line live; a pruned log, a state of another format or one that does not read means a replay from the start. It keeps the step ledger (`ledger`), the checks (`checks`: the statement parser, a run's worktree and exit code, running checks and checks sent to the background, the feed's checks, and the typical durations with the 2-minute rule: their recording, median and lookup, which `lib.rs` calls), each turn's files (`turn_files`) and the facts Ask shows (`ask`).
  - Only live lines request cards and notifications.
- `understanding/`: the understanding layer's I/O: the writer interface (turn summaries, goals, "Design so far", Ask, names and risk notes), the `claude -p` writer and the other CLI writers (agy, Codex, Copilot, Cursor) in `writer.rs`, the API-key writers' HTTP calls (`http_writer.rs`: Anthropic's API and an OpenAI-compatible one) and a fake, the worktree fingerprint, the card store with the briefs, the turn summaries, Turn writing (`turn_writing.rs`: what a turn's end and a worker's return write, on a queue for each session), which files are logic and which are tests (`logic_file.rs`), Claude Code's version kept beside the event log, and `weekly`, the command that prints the drift: unrecognised wake-ups and version changes.
- `workbench/`: workbench git (danielrispler/Falinks#328, module 7): a folder's main checkout, `fetch` and what removing a task's worktree would lose; the `gh` to run; other agents' resume commands; and agy's plugin. What only its own tests used is in `archive/workbench/` (#415).
- `system-map/`: `studio-system-map`, a library and the `system-map` binary that check `system-map.json` against the repository and say which parts a change touches (`docs/studio/behaviour/map.md`). `npm run check` runs `system-map check` after the tests.
- `server/`: `studio-server`, the state and the logic behind the page's commands, and the `plotkeeper` program that serves it (`src/bin/plotkeeper.rs`, the local page in `src/web.rs`, one function for each command in `src/api.rs`). Its modules include the read loop (`read_loop.rs`), the Map view's (spec #306: `map.rs` the payload, Daniel's positions and tiers and the guarded `git fetch`; `fog.rs` the commits since Daniel last caught up, kept per part, and what reading a brief clears; `history.rs` a part's history, the map at a past commit, a commit's files and a PR's; `ci_laws.rs` the default branch's last finished CI run, the law tests that failed in it and the words for a failed check; `stop_rules.rs` the usage log and the one-time review's counts) and the PR briefs' (spec #334: `prs.rs` which PRs are ready, `pr_briefs.rs` writing, keeping and rewriting the briefs, `ratify.rs` what Daniel accepted or overturned), `settings.rs` (with the API keys' Keychain store), `install.rs` (`plotkeeper install` and `uninstall`: the harnesses' plugins and hook files, and what it records to undo them; [install](plugin.md)), `hook_copies.rs` (the hook binaries' copies in the data folder's `bin/`, #356) and `runner.rs` (the [background runs](behaviour/background-runs.md), spec #378: the queue, the `claude` command with its sandbox block and allow list, a run's lock, status and outcome, Cancel, and the logic of the launcher, the crate's second program `plotkeeper-run`, `src/bin/plotkeeper-run.rs`), `back_a_law.rs` (Back a law, #398–#401: the clone, plotkeeper's own proof of a run's patches in `srt`, the kept patches, Open draft PR, and a new law drafted from a PR's brief) and `micro_worlds.rs` (micro-worlds, #399: the run, the host checks under the network guard `micro_world_guard.mjs`, the kept pages). `ui/`: its TypeScript page.
- `archive/`: retired code, never built, tested, linted or formatted (#415; its `README.md`): the Tauri desktop app (`src-tauri/`) and the daemon that owned its terminals (`terminal-daemon/`, danielrispler/plotkeeper#334, #332; each folder's `README.md`), the spikes, `real-calls.sh`, and the code and tests that only their own tests used.

The window calls the shell only through `invoke` (`ui/dom.ts`), which takes a command of the `Commands` map in `ui/types.ts` and gives its reply that command's type. The snap fixtures (`scripts/snap/fixtures.ts`, `rail-fixtures.ts`) are typed against the map, and `scripts/snap/base.ts` answers every command whose reply the window reads, so `npm run build` (`tsc -p scripts/snap`) fails on a reply that lacks a field, and on a command `base.ts` does not answer. A fixture may leave a command out: each starts from `...base`.

The Rust half of that map is checked by the wire tests (#246), with no code generator: `core/tests/wire.rs`, `understanding/tests/wire.rs` and `server/tests/wire.rs` serialize real values of the types the shell sends (sessions replayed from the fixtures, the session list's rows, the selection, checks, a subagent's log, a session's cards with its brief and Open items, a turn's summary, Ask's facts, a hunk, a check's output, the workspaces, git state, branches, losses and plan usage, and the Map view's `MapState`, the `UserState` its commands return, #333, a project header's `Mark`, and the server's other replies, #374: a part's history, a commit's files, the proof, a PR brief and a part catch-up as opened, the waiting briefs, the ratify rows, the review's facts, the pre-flight's, Explore this's, Back a law's and Guard with a law's answers, the saved projects, why a session didn't touch a name, and who took a blocked command's answer) as the shell does, and write them as `const` literals, each typed with its mirror in `ui/`, into `scripts/wire/<crate>.ts` (`scripts/wire/samples.rs`). `tsc -p scripts/wire` then checks them: a typed object literal fails on a field its type does not have, so a field renamed or added in Rust, or a saved-only field (`skip_serializing_if = "crate::saved::unsaved"`) that reaches the wire, fails `npm run check`, as does a required field the wire lacks. A field the shell sends that the window never reads is optional in `ui/types.ts`, so the snap fixtures may leave it out; its removal from the wire passes, its rename does not. Each crate's test writes only its own file, and the files are gitignored, so a file whose test was deleted stays behind and fails `tsc` against a newer `ui/`. `npm run check` deletes `scripts/wire/*.ts` before the tests; by hand, do the same and run the wire tests before `tsc -p scripts/wire`, or it checks an older run's samples. The limit: the check sees only the shapes its samples produce, so an optional field no sample fills, or an enum value none holds, is not checked. Two replies are outside the law: `settings_files` (`server/src/settings.rs`) and `watch` (`server/src/answer.rs`) are built as a bare `serde_json::Value`, so there is no Rust type to sample; their mirrors, `SettingsFiles` and `Ask`, are checked by nothing but the window's own use. Replies that are a string, a number, a map of strings (`map_place`) or nothing have no shape to drift.

`npm run snap:rail -- <folder>` renders the rail's states from fixtures in Chrome, which `npm run check` leaves out. `npm run snap:all` renders every fixture once, one per core at a time, and fails if one ends in `snap:fail` or an uncaught error in the page, and when Chrome itself exits non-zero it prints Chrome's exit status and the tail of its stderr first; CI runs it in a job of its own, beside `npm run check`. `npm run snap:readme` draws the README's three pictures into `docs/studio/assets/readme/` the same way.

`node scripts/review/outside-review.mjs [--force] [--model <id>] [--out <folder>]` is the outside review (#279): Gemini, through `agy`, reads a risky diff before its PR is opened (`AGENTS.md`, "Finish with a PR"). It reads HEAD's commits since the merge-base with `origin/main`, and only when the diff changes a struct or enum that derives `Deserialize` outside a `tests/` folder (judged from the whole type in the file after the change, not from the changed lines), a hunk of code that names one of the card store's files, or the turn-writing job queue (`understanding/src/turn_writing.rs`), or when the branch's issue has sub-issues, a spec. `--force` reviews any diff. The review has one round: the fixes of its findings get no second review. Any other diff prints `skipped: no risk match`. The review is one `agy -p` run with `gemini-4-neon-medium`, in a throwaway folder that holds a detached worktree of HEAD, the diff and the file lists. `scripts/review/deny-hook.mjs` denies it every tool but a read inside that folder (#283) and `finish`, through which `agy --json-schema` hands over its answer, and `PLOTKEEPER_TERMINAL_ID` is removed, so Studio shows no session for it. Afterwards the script checks that the throwaway tree is clean, says so if it is not, and removes it; killed mid-review, it ends `agy` and removes the tree first. It prints `reviewed: <n> findings`, then the findings' JSON file (in `--out`, else the system's temp folder), the minutes, the tokens and the Gemini quota left before and after. Whatever stops it (no `agy`, the 15-minute cut, a used-up quota) prints `review unavailable: <reason>` and exits 0; only a wrong option exits 2, before any review. Every run, whatever its verdict, also appends one line to `local-evidence/outside-review/runs.jsonl` in the main checkout (the time, branch, head, base, verdict, why it ran, model, round, findings, tokens, seconds and the quota before and after), and a reviewed run's findings file is kept beside it (#302); it records only where git ignores `local-evidence/`, and a record that cannot be written changes nothing else. `ui/tests/outside-review.test.mjs` tests the decision, the options, the `agy` call, the verdicts and the hook, and runs the script in a scratch repository with a stand-in `agy`; the real `agy` run was checked by hand (`local-evidence/2026-11-22-outside-review/`).

`npm run lint` runs Biome over the TS, JS, HTML and CSS, lint only (`biome lint --error-on-warnings .`, `biome.json`), and fails on a warning as on an error: it never formats or rewrites a file, and it leaves out what git ignores, `archive/` and `docs/studio/mockups/`. It also turns off nine idiom rules the page uses on purpose, such as the comma operator and assignments in expressions.

`npm run check` runs them all in order: `cargo fmt --all --check`, `npm run lint`, `npm run build`, `cargo clippy --locked --workspace --all-targets -- -D warnings`, `rm -f scripts/wire/*.ts`, `cargo nextest run --locked --workspace` (the shell included), the map check (`cargo run --locked -q -p studio-system-map -- check`), `tsc -p scripts/wire` on the samples the wire tests just wrote, and `npm run test:node`. nextest runs the same tests as `cargo test`, but runs every test in a process of its own, all binaries' at once; install it with `brew install cargo-nextest`. CI runs `npm ci` and `npm run check` in one job, and `npm run build` and `npm run snap:all` in another, in `.github/workflows/studio.yml`, on macOS. It runs for each push to `main` and for each pull request that is not a draft: a draft runs nothing until it is marked ready, then each push to it runs. A change to Markdown files alone, or to `archive/` alone, runs neither job. The engine's `checks.yml` and `ci-checks` skip the studio.

## The npm package

`npm i -g plotkeeper` installs plotkeeper on a Mac with no Rust (#368). The package is `npm/`: its `package.json` and, once built, a `bin/` with `plotkeeper`, `plotkeeper-hook`, `plotkeeper-answer` and `plotkeeper-run` (the launcher of a [background run](behaviour/background-runs.md)) side by side, each a universal binary (Apple silicon and Intel), the page embedded in `plotkeeper`. npm links `plotkeeper` onto the PATH; each start copies the other two into the data folder's `bin/` (#356), which the hooks call, so a switch of Node version leaves them recording. `npm run pack:npm -- <folder>` (`scripts/npm/pack.sh`) builds the page and both architectures, which needs `rustup target add aarch64-apple-darwin x86_64-apple-darwin`, and packs the tarball into the folder. `npm run smoke:npm -- <tarball>` (`scripts/npm/smoke.sh`) installs it with `npm i -g` into a throwaway home and npm prefix with no Rust on the PATH, and checks `plotkeeper --version`, the four binaries, `plotkeeper install` with a stand-in `claude`, a start that serves the page, and a hook that still records once the package is removed.

`.github/workflows/release.yml` runs both on every run: it packs on macOS and installs the tarball on an Apple silicon and an Intel runner. It runs on each push to `main`, by hand, and for a pull request that is not a draft and touches what the package is built from: `Cargo.lock`, a `Cargo.toml`, `rust-toolchain.toml`, `package.json` or its lock, `npm/`, `scripts/npm/`, a `plugin*/` folder or the workflow itself. A pull request's other changes, an Intel-only build break among them, show in it only after the merge to `main`.

### Cutting a release

1. In a PR, set the new version in `npm/package.json` and in `server/Cargo.toml` (`plotkeeper --version` prints the latter; `server/tests/plotkeeper_bin.rs` fails when they differ), with `Cargo.lock` updated by a build. Merge it.
2. In GitHub's Actions tab, run "npm package" on `main` with "publish" ticked. Daniel alone does this. The workflow publishes the tarball its own smoke jobs tested, with provenance, using the repository secret `NPM_TOKEN` (an npm automation token for the `plotkeeper` package). Without "publish", or from another branch, it only builds and tests.

## Recorded logs

Three fixtures in `core/tests/fixtures/` are real event logs, scrubbed by `scrub` (`core/src/bin/scrub.rs`). Each event keeps its shape and loses its content: text becomes `…`, and lists and objects become empty, except for what stays. What stays: ids, event names, `cwd`, the permission mode, a session's start source and end reason, agent ids and types, the `description` of a spawn or a Bash command, `isolation`, the paths of the files a tool reads or writes, skill names, the types and statuses in tool results, background tasks without their commands, exit codes, numbers, flags and timings.

An MCP tool keeps no text. Transcript and output paths become `…`. A prompt keeps only the markup Claude Code adds, with its ids and statuses, so a wake-up stays one; any other tag becomes `<…>`. A last message that asks Daniel something becomes `…?`.

- `checkpoint-day.jsonl`: the events of 2026-10-30, the checkpoint day of danielrispler/Falinks#347. Some of its sessions were still open at midnight.
- `subagent-run.jsonl`: a scripted session in a temporary repository that spawns a worktree worker and a read-only helper in the background, then stops the helper.

- `blocked-run.jsonl`: an interactive session in auto mode, in a temporary repository, whose foreground and background nested `claude -p` are blocked, allowed by a fake studio, retried and run, with the background one's wake-up. A command stays only when it carries the marker `studio-fixture-`; a wake-up's summary keeps its status and exit code and loses its quoted description. `core/tests/blocked_commands.rs` replays it.

Re-record the second when Claude Code's version changes. The script runs a nested `claude` on your subscription, so run it yourself, outside auto mode:

    core/tests/record-subagent-run.sh

Quit the studio app first: it would take the session as live and ask for cards. The script builds `plotkeeper-hook`, runs the session with this checkout's plugin, and scrubs the session's events from the event log into the fixture. Before you commit the new fixture, run `cargo test` and check that each text it keeps is a label, an id or a path.

Re-record the third the same way, with Claude Code's version, or when the blocked-command hooks change: quit the studio app, then run `core/tests/record-blocked-run.sh` straight in a terminal, with its output not redirected, since the session is interactive (an `ask` has no prompt to go to under `claude -p`). Watch the agent, and type `/exit` after its last reply, once the background command's wake-up has come. Ctrl-C is ignored by the script but ends `claude` early. The script plays the studio (heartbeat, one-time pass and Allow answer) and gives the session an `autoMode.hard_deny` rule through `--settings` so auto mode blocks its marked commands. It writes the fixture only when the log holds a `PermissionDenied`, a `StudioAnswer` and a wake-up for the session, and names what is missing otherwise.

The app tells you when the version changed. At a session's first `Stop`, it reads Claude Code's version from the session's transcript, the `.jsonl` file at the event's `transcript_path`, and opens no other file. It keeps each new version, with when it was first seen, in `claude-versions.txt` beside the event log. A version that differs from the last one kept shows a one-line notice at the top of the pane, a line in the Studio log, and a line in `weekly`. The first version kept has nothing to compare with, so it shows nothing.
