# Install and uninstall

plotkeeper records an agent's sessions through hooks, which run on each of its events. Wire them once, from any terminal:

    plotkeeper install

Install works at user level, never in a repository, so your git trees stay clean. It prints each step, and a harness it does not find on the `PATH` is skipped with one line:

- It copies `plotkeeper-hook` and `plotkeeper-answer`, from beside the `plotkeeper` executable, into the data folder's `bin/` (`~/Library/Application Support/plotkeeper/bin/`). Every hook names that folder, in quotes since the path has a space, never a checkout or an npm folder, and each `plotkeeper` start brings the copies up to the binaries beside it (#356), so an upgrade reaches the hooks at the next start.
- **Claude Code**: it renders `plugin/` with that path into `plugins/claude/` in the data folder, as a local marketplace of one plugin, and runs `claude plugin marketplace add` on it and `claude plugin install plotkeeper@plotkeeper`. `claude` writes `enabledPlugins` and `extraKnownMarketplaces` into `~/.claude/settings.json`; plotkeeper never opens that file (AGENTS.md, Hard rules), and puts no hook in any `settings.json`. The plugin shows as `plotkeeper@plotkeeper` in `claude plugin list`.
- **agy**: it renders `plugin-agy/` with the path of `plotkeeper-hook` into `plugins/agy/plotkeeper/` in the data folder, and installs it with `agy plugin validate` and `agy plugin install`, which copies it into `~/.gemini/config/plugins/plotkeeper/`. A copy already there is backed up first.
- **Codex**: Codex has no command for its hooks, so install adds plotkeeper's entries to its user-level hook file, `~/.codex/hooks.json`, after a backup, beside any hooks of your own there, and makes the file when there is none. They are rendered from `plugin-codex/hooks.json`: on eight events (`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `Stop`, `Interrupt`) Codex runs `plotkeeper-hook --agent codex`. Codex runs a hook only once you have trusted it, so install ends with that step: run `/hooks` in Codex once and trust plotkeeper's hooks. The file holds no credentials (Codex's hook docs give it no field for a key or a token); install never opens `~/.codex/config.toml`, which can. While installed, the file's keys are written in sorted order.
- **Qwen Code**: not wired yet. Its hooks live in its user-level `~/.qwen/settings.json`, which can hold API keys (Qwen Code's [authentication docs](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/auth/) put them in its `env` block), so install does not open it (AGENTS.md, Hard rules) until a way that never reads it is decided (#320). plotkeeper already reads Qwen Code's hook lines (below).
- **Cursor**, in its IDE or its CLI (`agent`), found by `~/.cursor` or by `cursor` or `agent` on the `PATH`: install adds plotkeeper's entries to the user-level hook file, `~/.cursor/hooks.json`, after a backup, beside any hooks of your own there, and makes the file when there is none; never a project's `.cursor/hooks.json`, which would dirty the repository and runs only in trusted folders. They are rendered from `plugin-cursor/hooks.json`: on seven events (`sessionStart`, `sessionEnd`, `beforeSubmitPrompt`, `postToolUse`, `postToolUseFailure`, `afterAgentResponse`, `stop`) Cursor runs `plotkeeper-hook --agent cursor`. The file holds no credentials (Cursor's hook docs give it a `version` and a `hooks` object, with no field for a key or a token), and install opens no other file in `~/.cursor`. While installed, the file's keys are written in sorted order.
- **The old setup**: so that no event is recorded twice, it removes what the archived desktop app set up, after a backup. In `~/.zshrc`, from each `export CLAUDE_CODE_PLUGIN_DIRS=` line, the entries that end in `plotkeeper/checkout/plugin` or `dev.falinks.studio/checkout/plugin` (the data folder's link into a checkout, by its name before #322); a line left with no entry goes, and so does the app's comment above it. With agy found, agy's old plugin `studio` is uninstalled.

The backups and a record of what install did are in `install/` in the data folder. A second install keeps the first backups and replaces its own plugins. Run it again after you change `plugin/`, `plugin-agy/`, `plugin-codex/` or `plugin-cursor/`: the agents run the copies install made.

To take it all back:

    plotkeeper uninstall

Uninstall puts `~/.codex/hooks.json` and `~/.cursor/hooks.json` back as they were (or removes one, when install made it); a file you changed after install keeps your changes and loses only plotkeeper's entries. It runs `agy plugin uninstall plotkeeper` and `claude plugin uninstall plotkeeper@plotkeeper` and `claude plugin marketplace remove plotkeeper` for what install added, installs the agy plugins it backed up again, puts `~/.zshrc` back as it was, and removes the data folder's `bin/`, `plugins/` and `install/`, and nothing else: the event log and the stores stay. A `~/.zshrc` you changed after install is left as it is, and uninstall names the backup to take the lines from.

## What Codex's hooks record

Codex's payloads are near Claude Code's, read by `core/src/codex.rs`: its prompts, tool calls (`Bash` as commands, `apply_patch` as edits, `mcp__…` as external tools), permission requests, turn ends and interrupts, and the model and permission mode each event names. Its transcript is not read, so a Codex session shows no context share, and no turn trees are recorded for it, so its turns list no files. Its subagents are not wired yet, and its questions and permission prompts stay in Codex's own terminal. The adapter is built from Codex's hook docs; a real run has not checked it yet.

## What Qwen Code's hooks record

Qwen Code's payloads are near Claude Code's, read by `core/src/qwen.rs` from lines its hook entries mark `--agent qwen`: its prompts (each turn by its `prompt_id`), tool calls (`run_shell_command` as commands, `write_file` and `edit` as edits, with how long each took, and `PostToolUseFailure` as a failed call), permission requests and notices, turn ends with the reply, the model `SessionStart` names and the permission mode each event names. Its transcript is not read, so a Qwen Code session shows no context share, and no turn trees are recorded for it, so its turns list no files. Its subagents are not mapped yet: a subagent's calls show as its parent's. The adapter is built from Qwen Code's [hook docs](https://qwenlm.github.io/qwen-code-docs/en/users/features/hooks/); a real run has not checked it yet.

## What Cursor's hooks record

Cursor's payloads have their own names, read by `core/src/cursor.rs`: a session is its `conversation_id`, and a turn its `generation_id`. It records prompts, each tool call whole at its end (`Shell` as commands, `Write` and `Delete` as edits, `Task` as a subagent's spawn, `MCP:…` as external tools; a failed call as failed), the agent's reply, turn ends (an aborted `stop` as an interrupt) and the model each event names. `preToolUse` and Cursor's other permission hooks are not wired: Cursor blocks the action when such a hook replies with nothing, so a running call shows only once it ends, and Cursor's questions and permission prompts stay in Cursor. Its transcript is not read, so a Cursor session shows no context share, and no turn trees are recorded for it, so its turns list no files.

Cursor also runs Claude Code's hooks, so one Cursor event could reach plotkeeper's Claude Code entry too. `plotkeeper-hook --agent claude` drops an event whose payload carries `cursor_version`, with one line on its stderr, and Cursor's own entry records it once, as Cursor's. In Cursor's IDE the hook's parent is the IDE's app, which outlives its sessions, so the hook records no pid for a process inside an app bundle (`….app/Contents/…`): such a session goes idle after a while with no event and is never ended by the process check. The CLI's pid is recorded and checked as Claude Code's is. The adapter is built from Cursor's hook docs; a real run has not checked it yet, nor whether Cursor runs Claude Code's plugin hooks (wave 1's trial).

## What the Claude Code plugin does

On thirteen hook events it runs `plotkeeper-hook --agent claude`, which appends the event to the event log. Answering from the page is Claude Code only: `plotkeeper-answer` holds a question, a plan's approval or a permission until you answer on the page.

Two hooks carry a blocked command (spec #170). On `PermissionDenied` for Bash, `plotkeeper-answer` leaves a request for the card and waits up to 600 s for Allow or Decline (timeout 610). On `PreToolUse` for Bash it claims the one-time pass Allow left and returns `"ask"`, or returns at once with no output when no pass matches. `PermissionDenied` is also logged by `plotkeeper-hook` like every other event.
