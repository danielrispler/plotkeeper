# Install and uninstall

plotkeeper records an agent's sessions through hooks, which run on each of its events. Wire them once, from any terminal:

    plotkeeper install

v1 supports Claude Code, Codex, agy and Cursor. Install wires Copilot and Qwen Code too, but they have not been trialled end to end, so they are v2, as are OpenCode and Cline, which nothing records yet ([decision](https://github.com/danielrispler/plotkeeper/issues/320#issuecomment-7127930696), #423).

Install works at user level, never in a repository, so your git trees stay clean. It prints each step, and a harness it does not find on the `PATH` is skipped with one line:

- It copies `plotkeeper-hook` and `plotkeeper-answer`, from beside the `plotkeeper` executable, into the data folder's `bin/` (`~/Library/Application Support/plotkeeper/bin/`). Every hook names that folder, in quotes since the path has a space, never a checkout or an npm folder, and each `plotkeeper` start brings the copies up to the binaries beside it (#356), so an upgrade reaches the hooks at the next start.
- **Claude Code**: it renders `plugin/` with that path into `plugins/claude/` in the data folder, as a local marketplace of one plugin, and runs `claude plugin marketplace add` on it and `claude plugin install plotkeeper@plotkeeper`. `claude` writes `enabledPlugins` and `extraKnownMarketplaces` into `~/.claude/settings.json`; plotkeeper never opens that file (AGENTS.md, Hard rules), and puts no hook in any `settings.json`. The plugin shows as `plotkeeper@plotkeeper` in `claude plugin list`.
- **agy**: it renders `plugin-agy/` with the path of `plotkeeper-hook` into `plugins/agy/plotkeeper/` in the data folder, and installs it with `agy plugin validate` and `agy plugin install`, which copies it into `~/.gemini/config/plugins/plotkeeper/`. A copy already there is backed up first.
- **Codex**: Codex has no command for its hooks, so install adds plotkeeper's entries to its user-level hook file, `~/.codex/hooks.json`, after a backup, beside any hooks of your own there, and makes the file when there is none. They are rendered from `plugin-codex/hooks.json`: on eight events (`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `Stop`, `Interrupt`) Codex runs `plotkeeper-hook --agent codex`, in the background (`"async": true`, from Codex's [hook docs](https://learn.chatgpt.com/docs/hooks)), so it never waits on it; Codex runs a `SessionEnd` hook in the foreground all the same. Codex runs a hook only once you have trusted it, so install ends with that step: run `/hooks` in Codex once and trust plotkeeper's hooks. The file holds no credentials (Codex's hook docs give it no field for a key or a token); install never opens `~/.codex/config.toml`, which can. While installed, the file's keys are written in sorted order.
- **Qwen Code**: its hooks would otherwise go in its user-level `~/.qwen/settings.json`, which can hold API keys (Qwen Code's [authentication docs](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/auth/) put them in its `env` block), so install never opens it (AGENTS.md, Hard rules) and wires an extension instead. It renders `plugin-qwen/` with that path into `plugins/qwen/plotkeeper/` in the data folder and runs `qwen extensions install <folder> --consent` on it, which copies it into `~/.qwen/extensions/plotkeeper/` (`--consent` skips the security prompt). A native extension's `qwen-extension.json` may carry a `hooks` object, which Qwen Code loads for every active extension; its extension docs do not say so, its source does (QwenLM/qwen-code at c134a03e5, `packages/core/src/extension/extensionManager.ts`, and `packages/core/src/hooks/hookRegistry.ts`: "Extension hooks are always loaded"), and its [hooks docs](https://qwenlm.github.io/qwen-code-docs/en/users/features/hooks/) run extensions' hooks after project, user and system ones. On nine events (`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `Notification`, `Stop`) Qwen Code runs `plotkeeper-hook --agent qwen`, in the background (`"async": true`), except on `SessionEnd`, which runs in the foreground since Qwen Code stops a background hook still running when it exits. plotkeeper opens no file under `~/.qwen`; `qwen` writes what it keeps of the install. The extension shows as `plotkeeper` in `/extensions list`. A real run has not checked it yet.
- **Cursor**, in its IDE or its CLI (`agent`), found by `~/.cursor` or by `cursor` or `agent` on the `PATH`: install adds plotkeeper's entries to the user-level hook file, `~/.cursor/hooks.json`, after a backup, beside any hooks of your own there, and makes the file when there is none; never a project's `.cursor/hooks.json`, which would dirty the repository and runs only in trusted folders. They are rendered from `plugin-cursor/hooks.json`: on seven events (`sessionStart`, `sessionEnd`, `beforeSubmitPrompt`, `postToolUse`, `postToolUseFailure`, `afterAgentResponse`, `stop`) Cursor runs `plotkeeper-hook --agent cursor`. The file holds no credentials (Cursor's hook docs give it a `version` and a `hooks` object, with no field for a key or a token), and install opens no other file in `~/.cursor`. While installed, the file's keys are written in sorted order.
- **Copilot** (its CLI, and VS Code's agent, which shares its hooks): it renders `plugin-copilot/` with that path into `plugins/copilot/plotkeeper/` in the data folder and runs `copilot plugin install` on it, which copies it into Copilot's own plugin folder. On seven events (`sessionStart`, `sessionEnd`, `userPromptSubmitted`, `preToolUse`, `postToolUse`, `postToolUseFailure`, `agentStop`) Copilot runs `plotkeeper-hook --agent copilot --event <name>`: these camelCase payloads name no event, so each entry names its own. plotkeeper opens no file under `~/.copilot`, where Copilot keeps its settings and may keep its login; `copilot` writes what it keeps of the install. The plugin shows as `plotkeeper` in `copilot plugin list`. Whether VS Code's agent loads plugins the CLI installed is not documented; wave 1's trial (#369) checks it.
- **The old setup**: so that no event is recorded twice, it removes what the archived desktop app set up, after a backup. In `~/.zshrc`, from each `export CLAUDE_CODE_PLUGIN_DIRS=` line, the entries that end in `plotkeeper/checkout/plugin` or `dev.falinks.studio/checkout/plugin` (the data folder's link into a checkout, by its name before #322); a line left with no entry goes, and so does the app's comment above it. With agy found, agy's old plugin `studio` is uninstalled.

The backups and a record of what install did are in `install/` in the data folder. A second install keeps the first backups and replaces its own plugins. Run it again after you change `plugin/`, `plugin-agy/`, `plugin-codex/`, `plugin-cursor/`, `plugin-copilot/` or `plugin-qwen/`: the agents run the copies install made.

To take it all back:

    plotkeeper uninstall

Uninstall puts `~/.codex/hooks.json` and `~/.cursor/hooks.json` back as they were (or removes one, when install made it); a file you changed after install keeps your changes and loses only plotkeeper's entries. It runs `copilot plugin uninstall plotkeeper`, `qwen extensions uninstall plotkeeper`, `agy plugin uninstall plotkeeper` and `claude plugin uninstall plotkeeper@plotkeeper` and `claude plugin marketplace remove plotkeeper` for what install added, installs the agy plugins it backed up again, puts `~/.zshrc` back as it was, and removes the data folder's `bin/`, `plugins/` and `install/`, and nothing else: the event log and the stores stay. Of `~/.zshrc` install keeps only the lines it removed, and where they were, never a copy of the file. A `~/.zshrc` you changed around those places after install is left as it is, and uninstall prints the removed lines.

## What Codex's hooks record

Codex's payloads are near Claude Code's, read by `core/src/codex.rs`: its prompts, tool calls (`Bash` as commands, `apply_patch` as edits, `mcp__…` as external tools), permission requests, turn ends and interrupts, and the model and permission mode each event names. Its transcript is not read, so a Codex session shows no context size. The hook records its turns' trees as it does Claude Code's (#426), reading `turn_id` as the turn and an `apply_patch` as an edit of the first file its patch names, so its turns list the files they changed and their summaries' facts carry them. Its subagents are not wired yet, and its questions and permission prompts stay in Codex's own terminal. Wave 1's trial (#369, Codex 0.171 and 0.172) recorded each event once, under `codex`. Codex's TUI runs its hooks from its shared `app-server` daemon (under `~/.codex/packages/app-server-daemon/`), which outlives every session and sends no `SessionEnd` on Ctrl+C, so the hook records no pid for it and the session goes idle after a while with no event. `codex exec` runs its hooks itself: its pid is recorded, and it sends `SessionEnd`.

## What Qwen Code's hooks record

Qwen Code's payloads are near Claude Code's, read by `core/src/qwen.rs` from lines its hook entries mark `--agent qwen`: its prompts (each turn by its `prompt_id`), tool calls (`run_shell_command` as commands, `write_file` and `edit` as edits, with how long each took, and `PostToolUseFailure` as a failed call), permission requests and notices, turn ends with the reply, the model `SessionStart` names and the permission mode each event names. Its transcript is not read, so a Qwen Code session shows no context size, and no turn trees are recorded for it, so its turns list no files. Its subagents are not mapped yet: a subagent's calls show as its parent's. The adapter is built from Qwen Code's [hook docs](https://qwenlm.github.io/qwen-code-docs/en/users/features/hooks/); a real run has not checked it yet.

## What Cursor's hooks record

Cursor's payloads have their own names, read by `core/src/cursor.rs`: a session is its `conversation_id`, and a turn its `generation_id`. It records prompts, each tool call whole at its end (`Shell` as commands, `Write` and `Delete` as edits, `Task` as a subagent's spawn, `MCP:…` as external tools; a failed call as failed), the agent's reply, turn ends (an aborted `stop` as an interrupt) and the model each event names. `preToolUse` and Cursor's other permission hooks are not wired: Cursor blocks the action when such a hook replies with nothing, so a running call shows only once it ends, and Cursor's questions and permission prompts stay in Cursor. Its transcript is not read, so a Cursor session shows no context size. The hook records its turns' trees as it does Claude Code's (#426), reading `generation_id` as the turn, the first workspace root as the folder of an event with none, a `Write` or `Delete` as an edit and a `Shell` call as a command, so its turns list the files they changed and their summaries' facts carry them.

Cursor also runs Claude Code's hooks, so one Cursor event could reach plotkeeper's Claude Code entry too. `plotkeeper-hook --agent claude` drops an event whose payload carries `cursor_version`, with one line on its stderr, and Cursor's own entry records it once, as Cursor's. In Cursor's IDE the hook's parent is the window's extension host, which renames itself (`Cursor Helper (Plugin): extension-host <folder>`), so its pid is recorded: the session ends, by the process check, when its window closes, since Cursor sends no `sessionEnd` on quit. A finished chat in an open window stays at your turn. The CLI's pid is recorded and checked as Claude Code's is. Wave 1's trial (#369, Cursor 3.31 and CLI 2026.11.22) recorded each event once, under `cursor`, in both; neither ran Claude Code's plugin hooks. Cursor sends `afterAgentResponse` and `stop` a few milliseconds apart in either order; the reply is its turn's either way. The headless CLI (`agent -p`) sends no prompt, reply or `stop`, so it records no turn.

## What Copilot's hooks record

Copilot's payloads come in two casings, by the casing of the event name an entry is wired to: camelCase (`sessionId`, `toolName`, `toolArgs` as a JSON string), which install wires, and snake_case (`hook_event_name`, `session_id`, `tool_input`, with Claude Code's tool names), for PascalCase names. `core/src/copilot.rs` reads both: prompts, tool calls (`bash` as commands, `edit` and `create` as edits, by `path`) and failed calls, and turn ends. Copilot's payloads have no call id, so a call's start and end are paired by its tool and arguments; no turn id, model, reply text or permission mode, so a Copilot session shows none of those; its permission requests are not wired, since their payload is not documented, and stay in Copilot. Its transcript is not read and no turn trees are recorded for it. The adapter is built from Copilot's hooks reference; a real run has not checked it yet.

In VS Code, the agent's hooks run under VS Code's own processes, which outlive any session. When the process the hook would record is inside a macOS app bundle (`.app/Contents/` in its path, as `ps` names it, which VS Code's are), the hook records none, so the session is never ended by the process check and is marked "idle?" after the quiet period. Copilot's CLI in a terminal, VS Code's included, is its own process and is checked like any agent.

Copilot reads `.claude/settings.json` too; plotkeeper puts no hook there, so Claude Code's entry never records a Copilot event. If Copilot turns out to run Claude Code's plugin hooks, the agent guard drops a Copilot payload sent to another entry, as it does Cursor's, once wave 1's trial (#369) has found what marks one (`copilot_payload` in `hook/src/lib.rs`; none is documented).

## What the Claude Code plugin does

On thirteen hook events it runs `plotkeeper-hook --agent claude`, which appends the event to the event log. Answering from the page is Claude Code only: `plotkeeper-answer` holds a question, a plan's approval or a permission until you answer on the page. It runs as `plotkeeper-answer --agent claude`: Copilot's CLI loads a plugin laid out as Claude Code's, its hooks included (its [plugin reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference)), and Codex runs a plugin's `hooks/hooks.json` (its [hook docs](https://learn.chatgpt.com/docs/hooks)), so a payload with another harness's marker (Cursor's `cursor_version`) is let through at once, with no card, as `plotkeeper-hook` drops it.

Two hooks carry a blocked command (spec #170). On `PermissionDenied` for Bash, `plotkeeper-answer` leaves a request for the card and waits up to 600 s for Allow or Decline (timeout 610). On `PreToolUse` for Bash it claims the one-time pass Allow left and returns `"ask"`, or returns at once with no output when no pass matches. `PermissionDenied` is also logged by `plotkeeper-hook` like every other event.
