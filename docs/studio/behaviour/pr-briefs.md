# PR briefs

A **PR brief** is the story of one ready PR, written once by a sandboxed writer from facts code assembles, held to checks, and played on the Map view so Daniel understands what the PR changes before he merges it (spec danielrispler/plotkeeper#334). This is the one doc for it; [the system map](map.md) covers the view it plays on, the fog it clears and the part sheet. Vocabulary (PR brief, chapter, Ready for review, ratify, claim check) is in [`CONTEXT.md`](../CONTEXT.md).

Code: `server/src/prs.rs`, `server/src/pr_briefs.rs`, `server/src/part_catch_ups.rs`, `server/src/ratify.rs`, `server/src/fog.rs`, `server/src/stop_rules.rs`; `understanding/src/pr_brief.rs`, `understanding/src/pr_brief_check.rs`, `understanding/src/part_catch_up.rs`; `ui/map-sheet.ts`, `ui/map-tray.ts`, `ui/map-brief.ts`, `ui/map-model.ts`, `ui/map-ratify.ts`, `ui/ratify.ts`, `ui/stop-rules.ts`.

## Ready detection

The server asks `gh pr view <branch> --json number,title,isDraft,state,headRefOid,body,closingIssuesReferences` for each listed session's branch, in its session's project folder (spec #659), so a session that `cd`ed out of its repository still asks its own, on Landed's triggers, never on a timer: at once when a turn ends, and when the page gains focus or the Map view opens, through one cooldown of a minute per repository with an in-flight guard (`prs.rs`). A PR is **ready** when it is open and not a draft. Its head is kept in memory and replaced by a later lookup. Any PR number found still names its session ("PR #N").

A lookup of a ready PR (`pr_briefs.rs`):

- With no stored brief at that head, the brief is written at once, unless it was ready when `plotkeeper` started: then it is written at start only when its head moved within `briefBackfill.hours` (2 by default; the older name `catchUp.hours` is still read when it is absent) and it is among the 3 newest such heads; any other is written when Daniel opens it, and is looked at as usual after that (a PR that becomes ready while `plotkeeper` runs is written at once, as before). A stale brief's rewrite counts toward the 3 as well, so a PR whose brief is of an older head is held like one with none. The start is the first lookup that `gh pr list` answered: one that `gh` failed writes nothing and leaves the cap for the next. The 3 is a constant in the code, not a setting.
- A new head marks the stored brief stale. It is rewritten when Daniel opens it, or when two lookups in a row see the same new head.
- **Since you read** (spec #477, part B; #496). Before that, a new head H2 is weighed against the newest stored brief's head H1 and Daniel's read of it (`fog.reads`) (`pr_briefs::push_of`), once per head when the verdict is settled; one from a brief not fully read at H1, or from git failing, is worked out again each time, so finishing the read at H1 before the rewrite still carries it over:
  - read in full at H1, H2 descends from H1, and the diff H1..H2 fogs nothing at Daniel's tiers (as for a PR that gets no brief): the read carries over; the tray row says "New push touched nothing on your map";
  - read in full at H1, H1 still resolves, and the old and new ranges (each from its merge base with the default branch, merges left out) hold the same number of commits and the same multiset of `git patch-id --stable`: a pure rebase, and the read carries over; the row says "Rebased onto main, nothing new in the PR". A dropped commit is not a pure rebase;
  - read in full at H1, H2 descends from H1, and its merge base with the default branch moved (main was merged into the branch): H1..H2 holds main's changes, so the PR's own commits are compared, as for a rebase, and so is one patch-id of its whole diff from its merge base, which holds what a merge commit itself edits. The same patches carry the read over, and the row says "Main merged into the branch, nothing new in the PR"; otherwise the full brief is rewritten with "Rewritten: main was merged into the branch";
  - read in full at H1, H2 descends from H1, and H1..H2 fogs something: a **Since you read** story (#497), and the full brief at H2 is rewritten as above, with no note. See below;
  - any other case, H1 missing, or a partial read: the full brief is rewritten as above. Once it is, the row says "Rewritten: the branch was rebased", or, after a partial read, "Rewritten after a new push; you had read N of M" (N the chapters read at H1), or, when what H1..H2 fogs cannot be told, "Rewritten after a new push"; a brief never read has no note.

  Carrying the read over moves every chapter read of the PR from H1 to H2 and keeps the parts the chapters light (`fog::carry_read`, not `mark_read`, which clears every chapter of a brief lit differently), then copies the stored brief to H2 with `head` set to H2 and its link evidence and map check read again at H2 (`ratify::head_check` from H2's merge base with the default branch), since a rebase or a quiet push can move an import site, remove its file or break the map. So the PR no longer waits, the next lookup keeps the copy, and fog at merge runs from H2. The note is kept in memory, as the failed and quiet heads are: after a restart the row says "brief ready", while the carried read and the copied brief stay.
- **The Since you read story** (#497). It is written with the brief's writer, claim check and retry (`write_pr_brief`), from the facts of the diff H1..H2: the map, its diff and the law tags from H1 to H2, the PR's text and spec as for the full brief, and a "SINCE YOU READ" section that tells the writer to tell only what is new since H1. It is stored apart, in `pr-briefs/since/{pr}-{H1}-{H2}.json` (`BriefStore::since`), so the latest-brief lookup (`BriefStore::latest`), part catch-ups, Guard with a law and the history strip's Brief all still get the full brief; its record line goes to the same `pr-brief-records.jsonl`. When the same head is seen twice the story is written first, then the full brief; opening the PR before that writes the story, which opens, then the full brief under a claim of its own (when the story's write fails, the full brief is written and opens instead). The tray's first row of such a head is the story ("since you read", `BriefInfo.since` its title), or one row per chapter of a chaptered story (`BriefInfo.since_chapters`), so each can be read to its end; the full brief's rows follow them, marked "full brief", and open it past the story (`pr_brief`'s `full`), as do the story's own "Full brief" button, a part sheet's chapter and the history strip's Brief. The story plays as a brief of its own (its step places and chapter reads kept apart from the full brief's), with its own Partial facts, its Could break copy and its not-confirmed popover; its See the code shows the diff from H1 (`pr_diff`'s `base`), not the PR's whole diff; it has no stale-base or pre-flight line, which are the full brief's. Its chapters read to their end mark no chapter of the full brief read: once every chapter of it is, the page tells the server once (`brief_since_done`), which carries the read over from H1 to H2 as for a pure rebase (`fog::carry_read`: every chapter read, the parts they light kept), so the PR no longer waits. Which stories' chapters were read is kept while the page runs; the push's outcome, as the notes, is kept in memory, so after a restart a head whose full brief is stored and whose story is not gets no story.
- A PR whose touched parts would not fog at Daniel's effective tiers gets no brief (see Shape), unless it changes the map: nothing is written, it is not gathered again at the same head, and its tray row says "no brief: nothing you track changed".
- **The short brief** (#644, spec #634 "Short brief") is that exception. A PR that fogs nothing at Daniel's tiers but whose Map diff is not empty gets a brief made by code, with no writer call, no claim check and no record line (`short_brief`, `understanding/src/pr_brief/short.rs`): one step, "The map in this PR", whose sentence counts what the Map diff marks, each kind's noun once ("2 parts added, 1 removed, 3 edited, 4 links added, 1 law added."), counted per Ratify map item but for links, which count per line, as the canvas draws one line per pair of ends, then "and N changes with no mark on the map" for the rest (a held item, a changed link or law, a flow), which Ratify lists (`map_diff::counts`). The step lights the parts and actors the marks are on (a marked part or actor, a marked link's ends, a marked law's part), which the camera frames; since the PR fogs nothing, reading it clears no fog. The page's Ratify step follows it. It is stored per PR and head like any brief, `short` set, through the same path (`write_now` in `pr_briefs/write.rs`), with the head's link evidence and map check (`ratify::head_check`), and it opens, waits, goes stale and is carried across pushes like any brief; a carried short brief counts and lights the new head's Map diff, and one whose new head no longer changes the map is not carried, so the next lookup finds nothing to brief. Its tray row says "map changed" where a brief says "brief ready". It needs no writer, so it is stored, with its head's map check, also without `claude`. A full brief needs the writer: without `claude` a head that needs one stores nothing and keeps no failure, so the tray still says briefs need Claude and offers no retry, and a stored full brief is left as it is, neither marked stale nor gathered for at a new head. A PR whose maps differ only in layout has an empty Map diff and gets no brief (snap `mapBriefShort`).

The project header's quiet dot, the rail's row, the session row's brief mark and the history strip's "Brief" link all read the stored briefs (`briefs_waiting`, `any_waiting`); they are described in [the map doc](map.md), [the rail doc](rail.md) and [the sessions doc](sessions.md). A brief waits for Daniel until every chapter is read at the PR's current head: the header's dot, the rail's row and the row's mark stop counting it once it is, and count it again after a push; its tray row stays, to read again. The ready PRs are those of the sessions' branches and of the repository's open PRs (`gh pr list`), so a hand-made PR with no session reaches the tray; a lookup `gh` does not answer keeps what was known. A write that failed is not tried again at the same head until the brief is opened.

## The writer and its facts

`write_pr_brief` is the one call into the writer (`understanding/src/pr_brief.rs`). The model is `prBriefs.model` in `settings.json` ([settings](../settings.md)), Opus by default, read on each write, and serves the writer, the claim check and the retry alike; the effort, `prBriefs.effort`, serves the writer and the retry only, low by default; the claim check always runs at `claude`'s own effort, so a faster writer never comes with a laxer checker (#450, [Measured](#measured-450)). Briefs are always written with `claude -p`, whatever `summaries.writer` says. The writer is sandboxed with no tools: everything it reads is in the facts, which `build_facts` assembles from `gh` (`fetch_meta`) and `git` (`gather`):

- The PR's title and body, the spec or ticket it closes (the lowest-numbered of them, trimmed to the sections the writer needs), its checks' conclusions. `fetch_meta` also keeps every issue the PR closes (`closing`), which pre-flight matches through, with each one's parent ([the system map](map.md), "Pre-flight"). The closing issues are noted as the brief is written, so a pre-flight's "You expected …" line reaches only the briefs written after that pre-flight was made; a brief stored before it carries none.
- The map at the PR's head (or as of its birth for an older PR), the map's diff, and the parts the diff touches with their tier (Daniel's tier overrides the map's), laws, the tagged tests that back each law and whether this PR changed one, and the flows through them.
- **Shape**, decided by code: a touched part fogs when its tier is Core, or Interface-only and named in the map diff. Up to two fogging parts is a **single story**; more is **chapters by behaviour** (2 to 4, each one behaviour lighting every part it crosses), with an overview when a flow changed. SHAPE also names the map's Core parts under Daniel's tiers, the ones a chapter's gist depends on.
- The diff, hunk by hunk inside a 64 KiB budget (`BUDGET`): the logic files of the parts that must be lit first, then other parts' logic, then tests, then the rest, smaller files first within each. What was cut goes into a "DIFF NOT SENT" note, and the budget record says how much was sent and cut. The stored brief keeps its `partial_facts` (#488): the cut and partial files with the bytes sent and cut, the claim check's error, and the diff's source languages no extractor of the map reads. The reader shows them as one "Partial facts · N" chip (#491), one line per missing input; a brief stored before them, or a part catch-up, has only its `partial` flag and says "The diff was cut" without the list.

The reply is the brief: a title, steps (kinds Where, Before, Now, Must stay true, Could break, Not in the plan, Your turn), each with a heading, a short body, the parts it lights, the links its light runs along, quotes that cite the facts, risks, a figure drawn by code from the writer's labels (`states`, `sequence`, `compare`), a covered-by test and at most one check; and the decisions the agent declared. The writer writes no "also touched" lines (#489): a line it sends anyway is dropped, and a brief written before reads with its old lines. A chapter that lights a Core part (declared or lit by a step) carries a **gist** (#397): its whole story in one plain sentence of at most 30 words, which explain-back compares Daniel's line with; any other chapter's gist is dropped by code. A brief written before the gist reads with none. Decisions get ids from code at the first write, and a rewrite keeps an earlier decision's id when its text matches.

## Checks and the claim check

Code checks (`check_brief`) flag each item they concern, and the brief as a whole: word caps on headings and bodies, the banned words ("guarantee", "ensure", "cannot", ...) and phrases that leak the sandbox ("was not sent", "didn't see"), a quote that is not in the facts, a part, link, law or flow the map does not hold, a risk or hop that does not exist, a pick check whose test is not in the diff, an order check not keyed to a changed flow, chapter and step counts, a required part no chapter lights, a "Your turn" with no check, and a Core chapter's gist that is missing, longer than 30 words, more than one sentence, or holds a banned word or a leak (flagged on the gist).

The writer's step rules carry a **strength of claims** section (#450): a claim widened past what the facts name ("every", "all", "only" and the like), an old behaviour summed up in a phrase of its own, or a cause, origin or consequence the facts do not state is what the claim check sends back most, so the writer is told not to make them, with two claims the records show it flagging.

The writer, the claim check and the retry of one write share one **facts block**, byte for byte (`facts_block`): it goes to `claude -p` as appended system text (`--append-system-prompt`, after `claude`'s own system prompt), with the same flags on all three calls but the effort (see above), and each call's own rules and items go as its prompt. `claude -p`'s caching then serves the claim check's and the retry's facts from the writer's call. A shared start of the prompt is not enough: the smoke write of #450 showed no cache read that way, since `claude -p` marks only the end of the prompt for caching, while appended system text was read back (17,208 tokens, $0.012 against $0.141 for the same call uncached). The facts hold PR bodies, specs, commit messages and code that anyone with push access wrote, so moving them into the system text gives that text more weight with the model; the block is therefore fenced (`<facts>` … `</facts>`) and labelled as untrusted data to explain, never instructions, and the writer has no tools, so the most such text can do is bend what a brief says, which the claim check reads against the same facts (#450). Each call's record keeps the tokens it read from the cache and wrote to it. The writer bench (`understanding/examples/writer_bench.rs`) makes one real write of either kind on a recorded input, into a folder of its own, at a chosen effort, and prints each call's time, cost and cache tokens; it measured #450's changes against the recorded writes.

The **claim check** (`pr_brief_check.rs`) is a second sandboxed call that reads the same facts and the written brief and says, per item (steps with their check and risks, each chapter's gist, the decisions), whether the facts support it. The code flags and the claim flags go into **one retry** that rewrites only the flagged items; flags of a chapter or of the brief as a whole are left as the code set them. A gist is an item of its own (`gist N`, N its chapter), so a missing one is written by the retry. An item still flagged after the retry carries "not confirmed from the facts". A failed claim call or retry leaves the code-checked brief stored and says why in the record.

**Also touched** (#489, spec #477) is code's, not the writer's. `check_brief` sorts the PR's changed files that belong to no part a chapter's step lights (files of unlit parts, ignored files and unowned files) into `also_groups` on the brief, run again after the retry. A lit part's files, its tests included, are not in it: they are that step's. A file goes in the first group that matches, and each group keeps its files sorted by path with their lines added and removed, and its line total:

1. **No part**: owned by no part and not ignored, which happens only when the PR's map check fails ([the check](map.md)).
2. **Tests**: a folder `tests/`, `test/` or `__tests__/`, or a name `*.test.*`, `*_test.*` or `*.spec.*`. A file with a `@law:` tag at the head names its law.
3. **Config/build**: `.github/`, manifests and lockfiles (`*.lock`, `go.mod`, `go.sum`, `Gemfile`, `Pipfile`, `requirements.txt`, `bun.lockb`), and `*.toml`, `*.yml`, `*.yaml` and `*.json` at any depth.
4. **Docs**: `docs/`, and `*.md` at any depth.
5. **Ignored**: ignored files of none of the kinds above.
6. **Other**.

An ignored file keeps its `ignored` mark in any group; the reader tags it "ignored" in groups 2 to 4. The reader (#492) shows the groups on the last step of the last chapter, leaving out an empty one: each its name, its file and line counts, and its files, each tagged file with the laws its tags name on its own row ("@law: <id>"), with a See the code that opens only those files (`pr_diff`'s `paths`, filtered before the drawer's cap). The Ignored group is a plain list with its See the code (snap `mapBriefAlsoGroups`). A required part no chapter lights is flagged on the brief, "(in Also touched: it keeps its fog)" when its files are in a group. Guard with a law's draft hears one line per group.

## The writer's limits

Every writer call of the studio, the PR brief's, the claim check's, the turn summary's, the Goal's, Ask's and the risk note's judge, runs `claude -p` on your subscription, with `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` removed from its environment, in `card-writer/` beside the event log (`claude` only for briefs, whatever `summaries.writer` says). What it reads is untrusted text, so it runs with no tools (`--tools ""`) and no MCP servers (`--strict-mcp-config`), in safe mode, whatever your settings allow, and without `CLAUDE_CODE_PLUGIN_DIRS`, so its own sessions send no hook events. A change it is given is cut at 64 KiB, with a line that says how many bytes were cut; a brief's facts keep to their own budget (see [The writer and its facts](#the-writer-and-its-facts)). It writes in English, with code in backticks. A reply that does not parse is asked for once more; when the second fails too, there is nothing stored and one line in the Studio log ([storage](storage.md)).

`plotkeeper` started from a launcher may not get your shell's `PATH`, so at start it asks your login shell where `claude` is: `$SHELL -lc 'command -v claude'`, with `/bin/zsh` when `SHELL` is unset. Only the path comes back; the writer keeps the process's own environment. A login shell that is not interactive reads `~/.zprofile` but not `~/.zshrc`, so the line that puts `claude` on your `PATH` must be in the first. With no answer, it runs `claude` from its own `PATH`.

To run `plotkeeper` with a fake writer instead of `claude -p` (it then writes no PR brief):

    PLOTKEEPER_CARD_WRITER=fake plotkeeper

### Measured (#450)

#450's changes were measured before merging with the writer bench on recorded inputs: the 7 part catch-ups written before it (their fog lists rebuilt from the stored catch-ups; the rebuilt facts match the records byte for byte) and the PR briefs of #404, #425, #421 and #430. Each variant wrote all 11 once, with the strength-of-claims rules and the shared facts as appended system text; the baseline is the recorded writes, made before both.

| baseline (recorded) | brief | 4 | 257 s | $2.97 | not recorded | 9 | 4 | |

**Split is kept.** It is about as fast and cheap as low, and its claim flags, counted by a checker at full effort, do not rise against rules (1 against 4 on part catch-ups, 4 against 5 on briefs) or the baseline (12 and 9). Low was faster still but was rejected: it lowers the checker's effort too, so its few flags may come from a laxer check, and a weak checker lets bad work through. The rules alone took flags from 12 to 4 on part catch-ups; the figure ask put a figure on every catch-up, where 1 of the 4 stored ones before had one.

Caching worked as built: the claim check and the retry read 23,000 to 26,000 tokens each from the cache, the facts and `claude`'s own prompt, against 1,760 before. A different `--effort` keeps the cache: low's and split's writers, at effort low, read the facts that rules' writers, at `claude`'s own, had cached.

Caveats:
- **The bench's writers read a warm cache.** Low and split ran after rules within the cache's hour, so their writers read the facts back (28,164 tokens each on average) and cost about $0.04 a call. A real write's facts are new, so its writer starts cold: the smoke write's cold writer at low took 9.1 s and $0.25. A real part catch-up is so estimated at about 20 to 25 s and $0.35, against the recorded 52 s and $0.83 on average; this is an estimate, not a measurement.
- **Retries still run, from the code checks.** Split's retry ran on 6 of 7 part catch-ups though the claim check flagged 1: three for a figure label over 18 characters (Hook, Server at a2e1aab, Understanding at b8c0985; the figure ask puts more labels in reach of that cap), one for a body over 45 words (Core at b8c0985), one for a gist over 30 words (Understanding at a2e1aab), and one for its claim flag (Core at a2e1aab).
- **The PR brief inputs are not byte for byte the recorded ones.** Their facts are 36 to 132 bytes larger than recorded, since `gh` now reports the PRs as merged with their final checks; the part catch-ups' facts are identical.

The raw logs and per-write results are in Daniel's local evidence (`local-evidence/2026-11-24-usage-issues/bench/`).

## The record

Each brief written appends one line to `pr-brief-records.jsonl`, beside the briefs: the PR and head, the shape, the budget and what was cut, the code checks' flags, the claim check's flags before the retry and the ones that still stand after, the flags the stored brief carries, the count left unconfirmed, any claim or retry error, and each call's tokens, cost and wall time (`duration_ms`: the writer, the claim check and the retry each). It is for tuning prompts, caps and models from real data; nothing shows it. A brief is stored per PR and head under the data folder's `pr-briefs-by-project/<project>/pr-briefs/`, and a reader ignores fields it does not know.

## The tray and the view

The tray at the map's foot lists the project's ready PRs (`ui/map-tray.ts`): a PR whose brief is stored is one row, or one row per chapter, that opens it; one being written says "writing the brief…" and waits; one without a brief opens, and opening it writes it; one whose write failed says so and opens to try again; a quiet one says "no brief"; a short brief's row says "map changed". The page raises no browser notification and no tab-title count for briefs. Opening a row (`openBriefOf`) reads the brief, returns a scrubbed map to now, and plays it from the step it was left at. A stale or unwritten brief is written in the background: the open answers at once that it is being written, the panel and the row say "Writing the brief…" and the map stays usable, and the brief opens when it lands (`map-landed`), unless another open or a close came since. A write that fails or finds nothing you track ends the wait and the row says so; closing it with Esc keeps the step and finishing it starts it over (`map-brief.ts`, `map-model.ts`).

Playing: the light runs a step's links at one speed and each part lights as it arrives, the camera frames the parts the brief lights, the panel crossfades between steps, citations sit in quiet type ("What this rests on"), a step body's one phrase the writer wraps in `<b>…</b>` shows in bold (#446): the reader splits the body on `<b>` and `</b>`, makes a bold element of each paired span and puts every other run in as plain text, so an unpaired tag shows as written and the body is never parsed as HTML (part catch-ups use the same reader; snap `mapBriefBold`, `mapCatchUpBold`, `mapBriefBoldUnpaired`), and each step's own "See the code", under its words, opens the PR's changed files with their diffs (`pr_diff`) in the drawer above the brief. Under reduced motion a whole step lights at once.

**The Map diff** (#640, spec #634): opening a PR's brief also asks `pr_map_diff` (`server/src/ratify.rs`, built by `server/src/map_diff.rs`) for its Map diff, compared as Ratify compares: the merge base with the head while the PR is open, the squash commit with its parent once it has landed. When the PR changed the map, the brief plays on it from open to close: today's map of the default branch with each part, actor, link and law the PR added put in from the head, and each it removed kept as a ghost from the base. A part whose own name, purpose or caption changed says "Edited"; held items and paths alone mark nothing. Links are judged per pair of ends, as the map draws one line per pair: a pair on one side only is new or removed, and a pair on both sides has no mark whatever its links changed (kind, reason, direction), which Ratify's rows tell. A changed law has no mark either, and flows are not drawn. Main's own changes since the branch left it show unmarked. A step lights a new part or a ghost as it lights any part; an id on neither side is skipped, as before. Closing the brief returns the map to now. A PR whose maps give no Ratify map item, a reformatted file included, has no Map diff, and its brief plays on today's map as before. How the marks look is in [the map doc](map.md) (snap `mapDiffSplit`, `mapDiffSplitBrief`, `mapDiffRemoval`, `mapDiffRemovalBrief`, `mapDiffLitGhost`, `mapDiffClosed`).

The stale-base line (#494) says what `main` changed since an open PR's merge base that the brief relies on; the brief compares against that base, so it may be reading an older `main`. The server works it out each time an open PR's brief is opened (`stale_base` in `server/src/pr_briefs.rs`), from one net diff, `git diff --name-only <merge-base> <default ref>`, plus `system-map.json` at those two commits; there is no commit-by-commit walk. The parts it checks are those the brief's steps light. It counts:

- a changed file a lit part owns by the default branch's map;
- a change to the map's say on a lit part: a law on it or on a link at it (the brief's own law reading, not fog's, which skips laws on links), a link at it, a flow through such a link, or its `paths`. An item counts when it is at the part in either map and differs between them, so an added, removed or moved one counts;
- a change to `Cargo.toml`, `package.json`, `rust-toolchain.toml` or `tsconfig.json` at the repository's root. Lockfiles and manifests below the root never count.

When something counts, the panel shows one line under its head, above the step: "Main moved since this PR's base:" then the laws, links, flows, parts whose paths changed and files, each kind once, its first three names and a count of the rest, with no PR numbers. A merged PR's brief never gets the line, and nor does a brief when nothing counts (snap `mapBriefStaleBase`, `mapBriefNoStaleBase`).

"See the code" is per step (#490). A step's button shows only the changed files owned, under the map at the PR's head (the brief's; the default branch's when the head has none), by the parts the step lights: the page sends their ids as `pr_diff`'s optional `parts`, and the server keeps those files before the drawer's cap of 80 files, so a large PR never loses a lit part's files to the cap. The Ratify step's button, or the last step's when there is no Ratify step, shows every file. A step that lights only actors, or parts with no changed files, shows every file with the note "This step lights no changed files" (`stepCode` in `map-model.ts`; snap `mapBriefStepCode`).

Copy for the agent (#493): a quiet copy icon puts a prompt on the clipboard that stands alone for any agent. Code writes it (`agentPrompt` in `map-model.ts`), with no model: a line saying what to do, naming the PR and its branch while it is open; the item's words (a step's kind, heading, body and risks; a decision's text); a not-confirmed item's reasons, its flags without the sentinel; each citation as `from: "quote"`; and the changed files of the parts the step lights, as paths with no line numbers, which the page asks of `pr_diff` (`parts`) when the step is drawn. Citations carry no lines, so the prompt has no `file:line`. The icon sits beside a Could break step's See the code, one per step; inside the not-confirmed popover, for a step or a flagged decision; and on the No part group of Also touched, whose prompt says "assign these files to a part, or ignore them". It copies through Overturn's path (`copyOverturn`), and the copy toast, the fourth in the Notifications region, under the note toast, says so with the prompt's first 3 lines and closes after 6 s, held by a hover or the focus in it. When the clipboard refuses, the toast holds the whole prompt with a Copy button, Overturn's manual way, and stays until its ×. Overturn keeps its own inline note. A part catch-up has no PR and no copy icon (snap `mapBriefCopied`, `mapBriefCopyByHand`).

The card (#449, replacing #339's tallest step) is narrow: its text's measure plus padding, one width on every step and while the brief is being written. A step's figure sits under its words, never in a column beside them. Each step is as tall as its own content, up to a share of the map's height; above it the step scrolls inside the card, which keeps its scroll from reaching the map, while Back and Next stay outside the scroll. For assistive tech (#456), Back and Next put only the new step's title in the card's one hidden polite live region (the step itself is not live), the dots read "Step N of M", and each figure is named by its kind and items. The card sits at the map's foot and grows upward, with Back and Next as its last row, so they keep their place on every step; Next keeps one width as Check and Done. The layout is the stylesheet's: no height is measured in script. A step, a ratify step's decision with a flagged item, or a Ratify row the Map text review flagged shows "not confirmed from the facts"; the mark opens a popover anchored to it that lists the item's flags without that sentinel, and closes when the step changes (#491). The "Partial facts · N" chip sits under the card's head, built with the card, so it keeps open or closed across steps, and is absent when nothing was missing. Also touched's groups, or an older brief's "Also touched" lines, show on the last step of the last chapter. Esc peels the drawer, then an open not-confirmed popover, then the brief, then a scrubbed commit, then the part sheet, then the view.

**The reader explains itself** (spec #520, #524), under the same page-wide `explanations` setting as [the part sheet](map.md) (on by default): while it is on, each step's title has one muted line under it saying what that kind of step is for (Where, Before, Now, Must stay true, Could break, Not in the plan, Your turn; a part catch-up's steps read the same lines), the Ratify step's title its own ("Accept or overturn" or "Guard with a law"), and Also touched one under its heading; in Ratify, "Not yet ratified"'s line, worded as on the sheet, follows only the first undecided item. Each title and heading carries `aria-describedby` to its line; while off, no line is drawn and no attribute points at one. A `?` toggle beside Leave, the same as the sheet's beside its ×, flips the setting; it is built once per brief and keeps the focus, its pressed state and hint set again when the setting changes, and the step draws again at once (as does an open sheet). Every text is in `ui/explanations.ts`, at most 12 words, to "you". A Wait tip teaches the `?` and `studio::ToggleExplanations` (snap `mapBriefExplained`, `mapBriefRatifyExplained`, `mapBriefExplainedOff`).

## Chapters

A chaptered brief has one tray row per chapter ("2 of 3"); each opens on its own and resumes at the step left. A chapter's frame holds every part its behaviour crosses. The overview, when there is one, plays once per brief, before the first chapter opened. A single story is one chapter over all its lit parts.

## The check

A step's check is one prediction. A **pick** is answered in the panel: pick an option, press it again to take it back, then Check; a wrong answer shows the correction. An **order** check is answered on the map: tap parts into numbered slots, Check grades it, a wrong answer nudges the parts out of place and the right path replays along the links. Right or wrong, answering counts for the chapter. Nothing is scored.

## The end-of-story bar

The last step of each chapter (of a single story, the story's last step, after Ratify when there is one) ends with one compact **end-of-story bar** (`ui/story-bar.ts`): explain-back when the story has one, and **Skip**, styled on the brief's own tokens. The S key skips the whole bar while it is on screen and no docked card takes its own answer keys, never while typing nor with Cmd, Ctrl or Alt held. A part catch-up ends with the same bar, keyed by its part instead of a PR and chapter. Its 1 to 5 rating and its note are gone (#448, spec #443, reversing part of #393): nothing read them back and no stop rule counted them.

On a Core part's story the bar's first row is **explain-back** (#397): an optional one-line field (at most 300 characters, autocomplete off, its placeholder an example ending in "…") where Daniel says the story back in his own words. Enter keeps it and shows it again with the story's gist under it and three marks, Got it, Partly and Missed, a radio group with a legend in which each label and its radio are one hit target; a mark can be changed while the bar is open. An Enter that confirms an input method's composition does not submit the line. It shows only when the story has a gist and one of its parts (the chapter's declared and lit parts, or the catch-up's part) is Core under Daniel's tiers now (`explainsBack`); any other story's bar holds Skip alone. The line is an input, so S and the window's single-key shortcuts do not fire while it is typed. A skip only closes the bar and logs nothing. The marks are words, never a number, and nothing of it is read back.

What the bar is given goes to `stop-rules.jsonl` through `story_bar` (`server/src/story_bar.rs`), which is its only store: one line per event, keyed by project and by `pr` and `chapter` (or by `part`), with the bar's own fields beside the usual ones:

- `explain-back-given`: an explain-back line was kept, with `line`, trimmed; one per bar.
- `explain-back-marked`: the line was marked, with `mark` (`got-it`, `partly` or `missed`); a changed mark logs again.

The server refuses a line that is not one of these kinds, including the removed `rating-offered`, `rating-given`, `rating-skipped` and `note-given`, which an older log's lines now read as an unknown kind that counts for nothing; it also refuses one that keys no story or both kinds of story, or carries a line or mark that does not belong to its kind. The review counts these kinds like any other; only the explain-back row reads one: explain-back is kept at 3 or more `explain-back-given` in the window, with no exception.

## Fog clearing

A chapter is **done** when its last step's words were seen (`watchSeen`) and its check was answered, right or wrong, when it holds one (`chapterGate`). The page tells the server once (`brief_chapter_done`), only for a chapter finished while the page is visible and focused (`watchSeen` already asks for both), which keeps "read at head X" per chapter in `map-state.json` and clears the PR's fog (`fog.rs`) from every part whose chapters are all done, lifting the mist. A part no chapter lights keeps its fog; leaving mid-chapter clears nothing. A PR read before it merges files fog at merge only for what was pushed after the read, limited to the paths the squash commit changed. "I know this" on a part's sheet still clears a whole part. Reading a [part catch-up](#part-catch-ups) to its end clears the fog entries it covered and no others: an entry that landed after it was written stays. Details of the fog are in [the map doc](map.md).

## Part catch-ups

A **part catch-up** (spec #378, #391) is one story of everything that landed in one fogged part since Daniel last caught up, played in this reader. It exists for fog no single brief explains: a part fogged by more than one entry, by a commit pushed with no PR, or by a PR whose brief is missing (never written, or its write failed) or lights no chapter on that part (read from the stored brief's lit parts). A part fogged by exactly one PR whose brief has a chapter lighting it opens that chapter instead (`part_catch_ups.rs`, `offer`; the map's state carries each fogged part's offer as `catch_ups`).

- **The sheet** (#636). A fogged part's sheet leads with the catch-up card under the part's name, caption and marks (`catchUpCard`, `ui/map-sheet.ts`; [the map doc](map.md) has the rest of the sheet). The card says how many changes landed since he last caught up (`changesLine`, `ui/map-catch-up.ts`) and, once the part catch-up is stored, shows its outline from the offer: its title and one row per step (kind and headline), never its gist, which stays behind Explain-back. Under them sit the part catch-up as the main button, "Catch up · N steps" (or "Read #N's brief", for that one chapter), and "I know this" as the quiet second (`fogActions`, `ui/map-catch-up.ts`). While one is written the card shows its stage, and a failed write says so and the button tries again. A part with no fog shows "Caught up" and the Refresher in the card's place.
- **Written when a turn ends and when the map shows** (#396, #635). At the end of any session's turn (`part_catch_ups::turn_ended`, from `read_loop.rs`'s `Output::YourTurn`), in the background and for that session's main checkout, `origin` is fetched through the per-repository cooldown, the fog is refreshed without starting it, and the part catch-ups of at most 8 fogged parts whose effective tier is Core or Interface-only start writing (`turn_end`), so a catch-up is ready by the time he opens the map; the page hears `map-landed` and redraws the fog. A project whose map was never opened has no fog started, and a turn's end fetches and writes nothing for it. When a project's map is shown (page load, focus or project switch: the `map_state` calls with `fetch`, after the fog's refresh) the part catch-ups of at most 8 fogged Core parts start writing too (`show`, #450 raised #396's 3; it leaves Interface-only parts to the turn's end). Both write oldest fog first (the part whose oldest fog entry sits furthest down the history), with this doc's writer, sandbox and model (`prBriefs.model`), through the same selection (`write_ahead`). Only parts that get a part catch-up count, not a part that opens its one PR's chapter. One already stored for its part's fog list, being written, or failed for that list is not written again and still takes its place among the eight, so a second trigger starts no second write. Opening a sheet writes nothing, and the part catch-up of any fogged part that neither trigger wrote (one past the eight, or an Interface-only part before a turn ends) is written when pressed. There is no timer.
- **Written on click.** The part catch-up of any other fogged part is written when he presses it, in the background: the button says "Writing…", the panel waits at the story card's narrow width, the map stays usable, and the story opens when it lands, unless another open or a close came since. A write that failed says so on the button, and pressing it tries again. A press while a part catch-up over an older fog list is being written gets its write once that one ends, so the button never waits on a write that is not running; and an open that finds neither a stored part catch-up nor a write running stops waiting.
- **The stage** (#450). While a part catch-up is written, its offer in the map's state carries the call that runs: `writing`, `checking` (the claim check) or `fixing` with the number of flagged items the retry rewrites; each new call tells the page (`map-landed`). The waiting panel shows it, "Writing…", "Checking claims…" or "Fixing N problems…" (N counts every flagged item, the code checks' as well as the claim check's), beside an indeterminate progress bar named "Writing the part catch-up", both in a polite live region; under reduced motion the bar slides slowly rather than stopping. Nothing of the story shows before the claim check has passed it: there is no streaming.
- **Stored** per project and part under the data folder's `pr-briefs-by-project/<project>/part-catch-ups/`, with the fog list it covers (its entries' commits); a stored part catch-up is read as it is only while the part's fog list is that list, and is written again otherwise. While that list is an earlier one whose every entry is still in the part's fog, the map's state offers it as `older` (its outline and the entries it covers), and the catch-up card, while the new one is written, shows "Read the one you have" with those entries (#638); pressing it asks `part_catch_up` with `older`, which answers with it only while that still holds. It plays under its own fog list, so reading it to the end clears only the entries it covers and the newer one stays fogged. Each write appends a line to `part-catch-up-records.jsonl` beside it, in the brief's record format.
- **Facts** (`build_catch_up_facts`, `understanding/src/part_catch_up.rs`), from `git` only, inside the brief's `BUDGET`: structure first (the map at the newest entry, the map's diff from before the oldest entry to the newest, the part's laws with their tagged tests and whether the range changed one, the flows through it), then each entry's PR title and body (a squash merge's subject and message) or a direct push's subject, then one combined diff of the part's own files over that range. When over budget the code is cut first, and "DIFF NOT SENT" says what was; the entries are cut only if the structure and the entries alone leave no room.
- **Reply and checks.** Its instructions are its own head followed by this doc's step, figure and check rules, so a fix to those reaches part catch-ups too. Its head asks for the matching figure (`states`, `sequence` or `compare`) on a step that tells a state change, an ordered flow or a before/after (#450). The reply is a single story of 3 or 4 steps over the part, with a gist (asked for in the part catch-up's own head, and required whatever the part's tier); the same code checks (plus that step count), the claim check and the one retry run on it. Its check follows the brief's rule: a pick only when a tagged test of the part changed in the range, an order only when the map's diff changed a flow through the part, otherwise none.
- **Reading it to the end** (its last step seen, its check answered when it holds one) clears the fog entries the part catch-up covered, its fog list, from that part (`part_catch_up_done`); an entry that landed after it was written stays, and the next part catch-up covers it. A part catch-up rewritten for a new fog list opens at its first step, not where the older one was left. No PR brief is marked read, so each stays enterable. The project header's dot loses its fog reason once no Core part stays fogged, whatever cleared it.
- The reader shows "Part catch-up" where a brief shows its PR number, and has no "See the code" and no Ratify step.
- **A long fog list.** Over more than 3 fog entries, the stored part catch-up carries a line written by code, "This catch-up summarises the main shifts of N fog entries; the full list is below.", and the full fog list, oldest first (`summary`); the reader shows both under its first step, the list folded ("The full fog list (N)"), a PR by number and title and a direct push by its subject and short commit (`fogListLines`, `ui/map-model.ts`).

## Ratifying

The brief ends with a **Ratify** step listing what Daniel has not yet looked at (nothing is added when all is ratified): each map or law change the PR made (read by code from the map's diff, keyed by PR, kind and map id) and each decision the agent declared (keyed by PR and decision id). Each has **Accept** and **Overturn**. Ratifying never blocks anything; the merged map is in effect at once and the record (`ratify.json` in the data folder, per project) only says Daniel looked. Overturn records the decision and copies a self-contained prompt to the clipboard with `navigator.clipboard.writeText()`, the copy first, inside the click, since a browser may refuse the clipboard after a round trip (the PR number, its branch while the PR is open, the item's id and its wording) and says "Prompt copied, paste it into your agent"; if the clipboard refuses, the prompt shows in a small box with a Copy button. Nothing is typed into a session. The part sheet marks the same two buttons on a law row or a link at the part that landed after the project's first run with no record. A link the PR adds shows its **link evidence** (#499, spec #477 "Link evidence"): when the brief is written, `source_of` reads the PR's head in commit mode (`ratify::head_check`, `system_map::check_at`) and stores, for each link the head's map adds to the merge base's, the import sites of the computed edge its way, as `link_evidence` on the stored brief (none in a brief stored before it, or for a link that is not an `import` one, even one beside an import edge between the same parts). Nothing is extracted live in Ratify: `pr_ratify` joins the latest brief's evidence to the added link's row, and joins none while the open PR's head is not the one the brief was written at (a push since), since the new head's imports may differ. The row's second line shows one site, then "(+N imports across M files)" for the others; the site opens its code in the drawer, read from the brief's head (`ratify_site`, `git cat-file blob <head>:<file>`, so a directory is refused rather than listed, never the PR's diff, so an import the PR did not edit shows too), numbered, its line marked; the count opens every site in the drawer, each opening its code. Overturn's prompt adds the site list ("Its imports at the PR's head: …"). A removed link shows no evidence. **Lit marks** (#643, spec #634 "The canvas"): each map item's row carries the id of the mark it lights on the Map diff (`mark` on `pr_ratify`'s row, from `ratify::map_items`: `part:<id>`, `actor:<id>`, `law:<id>`, or a link's line, `line:<end>|<end>` with its ends sorted, since the map draws one line per pair; none for a flow or a decision). Hovering or focusing the row (any of its buttons) lights that plate, line or law diamond with a class of its own, `ratify-lit`, in the brief's ring tokens, and leaving or blurring it clears it, as does drawing the step again (Accept, Overturn, Back, Next) or closing the brief, since a row replaced sees no leave; one row lights at a time. Neither the brief's `.lit` (the brief adds and strips it) nor story-to-map's `.turn-lit` (cleared from every plate whenever the map repaints during a brief) is reused. A part's detail has a **Caption** Was/Now, so a part the Map diff marks Edited always has a row saying what changed, and a link whose ends swapped a **Direction** Was/Now (`a to b`, then `b to a`); the canvas marks neither. Snap `mapDiffRatifyLit`. **The head's map check** (#641, spec #634 "The head's map check"): the same `system_map::check_at` at the PR's head also gives the map check's problems, which are stored on the brief as `map_problems` for every PR whose brief is stored, external ones included, since it costs no model quota (a head with no `system-map.json` has none). For a PR not by Daniel's own GitHub login (`prs::by_own_login`: `gh pr view --json author` against `gh api user`, run as his normal `gh`; a `gh` that cannot answer counts as not his) the check is untrusted: the commit's `rust-toolchain` files are not copied into the temporary folder `cargo metadata` runs in, so the PR cannot choose the toolchain rustup resolves. Ratify's head, a slot above its items that holds one line per thing said about the head, then says "The map check fails at this head: N problems", a disclosure that opens to the problems as the check words them and stays open while the step is drawn again; nothing shows when the check passes, or in a brief stored before it. The line alone brings the Ratify step, titled "The map at this head", when nothing is left to ratify and no Guard with a law is offered (snap `mapBriefMapCheck`, `mapBriefMapCheckAlone`). **The Map text review in Ratify** (#645, spec #634 "Ratify's display"): opening a PR's brief also asks `pr_map_review` for its review at the PR's head ([background runs](background-runs.md)), and asks again when the server says it changed (`map-landed`). Its line sits in Ratify's head above the map check's: "Map text review: N checked, M flagged", "Reviewing map text…" while it runs, "Map text review failed" with its reason and **Run again**, or, for a PR not by Daniel's own login with no review yet, a **Review map text** button; both buttons start it (`map_review_start`), and nothing shows when the head changed no map text. A review that ends while its brief is open says its line once in the page's action region. A row the review flagged (an item id `part:<id>/…` or `held:<id>/<n>` on its part's row, `link:<id>/reason` on its link's, `law:<id>/text` on its law's) carries the "not confirmed from the facts" mark, whose popover gives per flagged field the verdict, the reviewer's why and the lines it cites (a held item named as the row's detail names it), with the copy-for-agent icon, whose prompt asks the agent to check the item's text in `system-map.json` against the code; an unflagged row shows nothing, Accept stays enabled, and Overturn's prompt adds "The map text review flagged it: …" with the same words. A review that runs, has flags, waits for **Review map text** or failed with **Run again** brings the Ratify step as the map check's line does (when it ends with nothing to say and that step goes while Daniel is on it, the brief stays open on its new last step, its dots redrawn), so both buttons stay reachable with nothing left to ratify; so does one that left items out, "N left out for an id it does not take" ([background runs](background-runs.md#map-text-review)). Only the latest request's answer is drawn: a read on `map-landed` or a start whose answer comes after a later one's is dropped, so a late "reviewing" never undoes "done" (snap `mapBriefReviewFlag`, `mapBriefReviewRunning`). The full rules, including the `since` date and `pending` records, are in [the map doc](map.md). One record is written without a click there: Open draft PR on a back a law patch (#400) records the law change of the PR it opens as accepted (PR number, `law`, the law's id) once `gh` returns the number, so a change Daniel started and reviewed is not offered to him again as unratified ([background runs](background-runs.md#back-a-law)).

## Guard with a law

A fixed bug can leave a law behind it (spec #378, ticket #401). When a brief is written, code reads two things from its facts: whether the PR closes an issue labelled `bug` (`gh issue view <n> --json labels` for each issue it closes, `PrMeta.bug`), and whether its diff adds a `@law:` tag or changes a tagged test (`LAW TAGS ADDED`, and the tagged tests marked "changed in this PR"). A bug fix that does neither stores **Guard with a law** with the brief (`guard`, the map's parts the PR touched), so the offer stays on the brief after the PR merges and is read as stored.

The brief's last step then holds a **Guard with a law** row beside Ratify's items (the step titled "Guard with a law" when nothing is left to ratify). It lists each law on trust of a part the PR touched, with **Back this law**, which starts a [back a law](background-runs.md#back-a-law) run, and **Add a new law**. Add a new law asks the PR briefs' writer, which has no tools, to draft one law from the brief's facts on one of those parts: the brief's steps (where the PR's and the issue's text reach it), the parts and their laws. The PR's text goes only to that writer. A confirm step shows the draft in fields Daniel may edit, the part, the id and the sentence, with **Start the run** and Cancel; when the writer gives no draft the fields are empty and the step says why. Only what he confirms reaches the run, which adds the law to the map with its tagged test in one patch, proven and reviewed like back a law ([a new law](background-runs.md#back-a-law)). Each run the row started says where its patch stands, as a law's row in the part's sheet does; a new law's rejected run offers Dismiss, not a second run.

## Stop rules

The brief's use is counted quietly in `stop-rules.jsonl`, with no setting and nothing shown, beside the map's own events ([map doc, Stop rules](map.md)). Each brief event names its project and PR:

- `brief-offered`: the PR's tray row was seen (`watchSeen`), once per PR; the server keeps the offer to one line however often the tray is drawn or Studio restarts. A row with no brief to open offers nothing.
- `brief-opened`: a tray row (or the rail's or history strip's link) opened the brief.
- `chapter-done`: a chapter was read to its end, as above.
- `check-answered`: a check was graded.
- `ratify`: Accept or Overturn was pressed, from the brief or the part sheet.
- `unconfirmed-seen`: a "not confirmed from the facts" mark was seen, once per PR in a window.
- `guard-offered`, `guard-started`: a brief's Guard with a law row was drawn (once per PR, kept to one line by the server as `brief-offered` is), or a run was started from it, backing a law or adding a new one. Started is an entered action.
- `catch-up-offered`, `catch-up-opened`, `catch-up-done`: a part catch-up was offered on a part's sheet (once per part in a window), opened, or read to its end. Opened and done are entered actions; "I know this" stays `know`, counted apart.

The review lists **part catch-ups** among the little-used modules when fewer than 3 were read to their end in the window (`table`, `ui/stop-rules.ts`). It lists **Guard with a law** when no run was started from it, judged only once it was offered at least 3 times.

The one-time review (14 active days and 20 merged PRs, whichever comes last) lists **PR briefs** among the little-used modules when briefs were opened for fewer than a quarter of the merged PRs that had one offered. Offered and opened are counted among the PRs merged since tracking began, so an abandoned PR counts for nothing. It also adds a sentence when "I know this" cleared more fog than `chapter-done` did, but only where briefs were offered. Never a score, a streak or a count on screen.
