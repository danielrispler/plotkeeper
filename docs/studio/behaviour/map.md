# The system map

`system-map.json` at the repository's root describes the system in plain words: its parts and the files each owns, the outside actors it talks to, the links between them, the files that belong to no part on purpose, and the laws that must stay true. `system-map check` holds the file to the repository, and `npm run check`, and so CI, runs it. The command and the library are the `system-map/` crate (`studio-system-map`); it assumes nothing about plotkeeper.

## The file

JSON, one object. A field the checker does not know fails the check.

- `version`: `2`. Any other value fails the check, and `touched` too, with a problem that names the value and says this checker reads version 2. A version 1 map fails the check with a problem saying to move it (below).
- `extractors`: optional, the names of the extractors to run (below). A map that names none gets no computed edges.
- `parts`: each has `id`, `name`, `caption` (a few words), `purpose` (the part's job, in one or two sentences), `holds` (below), `tier` (`core`, `interface` or `black-box`: the part's default; Daniel's own choice is outside the repository), `paths` (the ownership patterns) and an optional `zone`.
- `actors`: each has `id` and `name`. An outside actor owns no files.
- `links`: each has `id`, `from` and `to`, a part or an actor at each end, a `kind` and, for every kind but `import`, a `reason` (below).
- `ignored`: path patterns that belong to no part on purpose.
- `laws`: each has `id`, `on` (the id of a part, a link or a flow), `backing` (`check` or `trust`) and `text`, one plain sentence.
- `flows`: optional. Each has `id`, `name` and `hops`, each hop a `link` id and one plain sentence `text`. A hop may run its link backwards; the sentence says which way.

A part's `holds` is a list, which may be empty, of the named things it holds, each `{ "name", "text", "paths" }`: a name unique within the part, one sentence of `text`, and optional `paths`, the item's key files, in the parts' pattern syntax. Each of an item's `paths` must match a file its part owns. "One or two sentences" and "one sentence" are guidance; the check counts characters (spec #473):

- `purpose` at most 240 characters, a held item's `text` at most 140, and at most eight held items per part;
- an empty or blank `purpose`, held `name` or held `text` fails.

A failure names the part, the length and the cap, and says where the detail goes, for example `part "server": purpose is 3,986 characters, the cap is 240; keep the job here, move the detail into a held item or the area's doc, or split the part`.

**Version 1 maps.** A map with `"version": 1` is version 1, whatever its fields. One conversion in the crate, `system_map::convert`, takes a map's JSON text and returns version 2 JSON: each part's `description` becomes its `purpose`, untruncated, and its `holds` is empty; nothing else changes (a link without `kind` keeps none). A map of another version comes back as it was. The lenient reader (`parse_lenient`) converts first; the strict check still requires version 2. The server converts where it reads a map, a ref's (`server/src/map.rs`) and a commit's (`server/src/history.rs`), and stores and sends the converted text, so the page, ratify, staleness and the prompts see only version 2; fog converts both sides of each commit it walks, so an edited `description` in a version 1 project still fogs. One renderer, `system_map::part_text`, gives a part's purpose and held items as prompt text, for pre-flight, back a law (its draft and its run), micro-worlds and the part catch-up. A build from before version 2, 0.1.1 included, shows a version 2 map as unreadable.

A link's `kind` says what joins its ends (spec #473):

- `import`: a code dependency, which the extractors can prove. It runs from the dependent part to the part it depends on, as a computed edge does, and the check holds its direction. It takes no reason and never ends at an actor, since an actor owns no code.
- `http`, `spawn` and `file`: run-time links no extractor can see: a request over HTTP, a process one end starts, or a file one end writes and the other reads. `file` also covers a file embedded at build time, such as `include_str!` of the plugins' hook files in `server/src/install.rs`. These keep the reader's arrow, following the data, and their direction is not checked. Each needs a `reason`, one sentence of at most 140 characters on what crosses it; a blank or longer one fails.

One pair of ends may have an `import` link and run-time links both: the server imports the hook crate (`server-hook`, `import`), and the hook writes the event log the server follows (`hook-server`, `file`).

Ids are lowercase words joined by hyphens, unique across parts, actors, links, laws and flows. An id never changes when a name does. The checker only reads the file; edit it with ordinary tools.

## Who owns a file

"The files" are what git tracks; an untracked or gitignored file is never counted. A pattern is relative to the repository's root: one ending in `/` owns everything under that folder, `*` matches within one path segment, `**` matches across segments, and anything else names one file. Among parts the last pattern that matches a file wins, in the file's order. A file an `ignored` pattern matches belongs to no part, whatever the parts say.

## Laws and tags

A law with `backing: "check"` has a test that stands behind it; one with `"trust"` has none. A test is tied to its law by the text `@law: <id>` in a comment of its own line in the test's source, such as `// @law: wire-types-agree` above the test. One test may carry several tags and one law may have several tests. Every tracked file is searched, ignored paths included. A tag proves a comment exists, not that the test passes.

## What the check does

`system-map check [--json] [--root <dir>]` prints one line per problem and exits non-zero when there is one. A pass prints one line of what it covered, so a pass with nothing checked shows: `ok: 7 parts own 581 files (212 ignored); 18 links: 9 import (9 proven, 0 unproven), 5 http, 3 file, 1 spawn; 12 laws: 9 check, 3 trust`, where "ignored" counts the tracked files no part owns on purpose and an import link is "proven" when a computed edge runs its way and "unproven" when an end is a part no extractor reads (below). The root is the git top level of the current folder unless given. It fails, naming the file, pattern, id or law and what to change, when:

- the file is missing, is not JSON or does not match the shape above (an unknown field, a duplicate id, a link end, a law's `on` or a hop that names nothing, a tier outside the three);
- a tracked file is owned by no part and matched by no `ignored` pattern;
- a pattern of a part or of `ignored` matches no tracked file;
- a part's pattern names only `system-map.json`;
- a law says `check` and no tag names it, or says `trust` and a tag names it, or a tag names a law the file does not have;
- a link has no `kind`, or a run-time link has no `reason` or one past 140 characters, or an `import` link has an actor at an end;
- the link check fails (below).

The map file itself needs no owner and no `ignored` entry: `check` and `touched` both place `system-map.json` as ignored, and an `ignored` pattern that is exactly `system-map.json` never fails for matching nothing. So a new repository's map passes before and after it is first tracked.

**The link check.** A part is **read** when a named extractor reads at least one file it owns: `rust-modules` reads Rust files, `cargo` `Cargo.toml` files and `typescript-imports` script files. Between two read parts:

- an `import` link with no computed edge in its direction fails: a dead link, or a backwards one, whose problem says to turn it around;
- a computed edge with no `import` link in its direction fails, whatever run-time links join the pair, so a run-time link never hides a new dependency. (Before spec #473 such an edge was only a `note:`.)

An `import` link with an end that is not read passes as **unproven**, and the pass line counts it so: a part in a language no extractor reads (Go, Python) keeps its code dependencies as import links rather than mislabelled run-time ones. A map that names no extractor has every import link unproven. A problem names the link or the two parts and what to add or change, for example `part "core" depends on part "workbench" in the code, and no import link runs from "core" to "workbench"; add { "from": "core", "to": "workbench", "kind": "import" }, even beside a run-time link`.

`--json` prints the parts with their files, the links, each law with its tags (file and line), the problems, and the pass line's counts (`counts`: `parts`, `files`, `ignored`, `links` as `total`, `import`, `http`, `spawn`, `file`, `proven` and `unproven`, and `laws` as `check` and `trust`).

## The extractors

An extractor reads which tracked file depends on which; the checker turns each pair into an edge between the parts that own the two files and drops pairs inside one part or touching an ignored file.

- `cargo`: the workspace's crates and the workspace crates each depends on, from `cargo metadata --no-deps --offline`. Dev-dependencies are left out.
- `rust-modules`: `mod` declarations and paths, each resolved through the module tree of the crate it names to the file that defines the module (the longest stretch of the path that names a module). It reads paths in `use` lines and inline, anywhere in the code:
  - `crate::<module>::…`, from the file's own crate root;
  - a bare path whose first word is a module the file declares (or an inline module it sits in declares), such as `ci_laws::CiCache` in a crate root holding `pub mod ci_laws;`, or a name a `use` line brought in;
  - a path into another workspace crate, such as `studio_server::runner::launch`, which reaches `server/src/runner.rs`, not the crate's `lib.rs`. It is read only when the file's crate depends on that crate as a normal dependency (dev-dependencies are left out), or is that crate's own binary, test or other target. A crate is named by its library target's name in `cargo metadata`, not its package's (package `studio-system-map`, library `system_map`), or by the dependency's rename. When the repository has a `Cargo.toml` and `cargo metadata` fails, these paths are not read and the check prints one problem saying so; a repository without one has no workspace crates to read.

  Each pair of files counts once, however many paths join them. `self::` and `super::` paths are not read.
- `typescript-imports`: relative import specifiers resolved to tracked files. A specifier that resolves to no tracked file is skipped; a literal `import('./x')` is read, but a computed specifier or a path alias is not seen.

The checker runs only `git` and, when the map names `cargo` or `rust-modules`, `cargo`; it reads no file outside the repository, so it never reads through a tracked symlink (the link still counts as a tracked file for ownership), and needs no network.

## Which parts a change touches

`system-map touched [--json] [--root <dir>] [path...]` names the parts that own the paths, with the ignored paths and the unowned ones listed apart. It takes paths as arguments or one per line on standard input, so `git diff --name-only | system-map touched` works. It matches by pattern alone, so a deleted or moved path is still placed. A map that fails the shape check gets no answer: it fails with every problem `check` would report, one per line on standard error, and exit status 2.

## How well the parts follow the imports

`system-map imports [--json] [--root <dir>]` tests a cut of the code into parts. It reads the map and runs the extractors it names, and counts the file pairs they find (each pair once) whose two files a part owns. A crate root's `mod` and `pub mod` lines are left out of the counts, since they declare the module tree rather than use it; the same pair still counts when the root also writes a path into that module. A map that names `cargo` counts its manifest pairs too. It prints:

- one line of totals: the imports between owned files, how many are inside parts and how many across, and the across share raw and weighted;
- **hubs**: files whose degree (imports in plus out) is at least three times the mean degree, taken over the files with at least one counted pair (Bunch's rule). They are listed apart, and their pairs stay in the counts;
- **inside**: each part's imports inside it;
- **across**: each ordered pair of parts with the imports from the first to the second;
- **both ways**: the pairs of parts that import each other.

Every count is given raw and **weighted**: each pair weighs 1 / the fan-in of its target, the number of counted pairs into that file. So a hub that many files import adds little weight, and a utility file does not make two parts look tangled. The weighted across share is across weight over total weight.

It suggests no grouping. To test a cut, edit the map's paths and run it again. It exits 0 on any counts; an extractor that cannot run prints a `note:` and its pairs are missing from the counts. A map that does not load exits 2 with its problems on standard error, as `touched` does. `--json` prints the same numbers: `total`, `inside` and `across` (`raw`, `weighted`), `across_share` (percentages), `mean_degree`, `hubs` (`file`, `part`, `degree`, `fan_in`, `fan_out`), `parts` and `between` (each with `raw` and `weighted`), `both_ways` and `problems`.

## plotkeeper's map

Seven parts: the agent plugins, the hook, the core, the server (`server/`), understanding, the window (`ui/`) and workbench; three actors: the agents, the writer and GitHub; one flow, Turn writing. Seven links are `import` links, the crates' real dependencies (server on core, hook, understanding and workbench; core on workbench; understanding on core and hook), all proven; the rest are run-time links, among them the hook's `file` link to the server beside the server's `import` link to the hook. Turn writing's first hop runs from core to the server, against the `server-core` import link, and says so. `ignored` holds what is not the running system: the docs, `archive/` (retired code: the spikes and the desktop app and its terminal daemon, #332, #415), `scripts/`, the tooling crates (`wayfinder/`, `test-support/`, `system-map/`), the npm package's manifest (`npm/`, #368) and the repository's own configuration at the root. A change that adds, moves or removes files, changes what a part does or how parts connect, or changes a law changes the map in the same PR (`AGENTS.md`).

## The Map view

The window's Map view (`ui/map.ts`, `server/src/map.rs`) draws a project's map on a quiet chart: parts as plates (name, caption, a mark per law: filled when a check backs it, hollow when it rests on trust; a plate's hover text is its name, caption and purpose, never its held items), actors as labels, links from rim to rim. It is the page's base (#386): the page is Treatment C's frame, a 34 px top bar over the map, with the 252 px session list at the right on the darkest tone (`--chrome`), told apart from the map (on `--bg`, with a rounded top-left corner) by tone, never a border line. There is no centre column, and Home is retired ([ADR 0001](../../adr/0001-retire-home.md)). The page opens on the last viewed project's map (kept in the browser), else the first saved project's. The top bar holds the shown project's name, the Needs you chip and the gear; the map draws no title of its own. The session list's project headers switch the map: a click on another project's header shows its map (a session's panel of another project closes with the switch; History and Settings stay), and a click on the shown project's header folds or unfolds its sessions. Selecting a session, from its row, its chip or a key, shows its project's map with its story in the left panel. Each header carries the quiet dot Home's project row once had, unchanged in meaning (fog on a Core part, a broken law, or a PR brief waiting; `map_marks`), drawn as the map's mist; its hover names which of the three lit it. With no saved project (a fresh install) the map's place says "Run your agent in a repository; it appears here" with a link to the install docs; a project without `system-map.json` shows the draft prompt, which asks for each part's purpose and held items. Below 1007 px the list is its strip. `studio::ShowMap` (shift-cmd-m and shift-cmd-h by default), "back to the map", closes the left panel; a `keymap.json` that still names `studio::GoHome` gets the same action.

- **Source.** The server reads `system-map.json` with `git show` from `origin`'s default branch as last fetched, never the working tree. With `origin/HEAD` unset it reads the local `main` or `master` and says so quietly. It fetches `origin` when the view opens and when the window gains focus while it is open, and when a task is first seen merged; never on a timer. A repository is fetched at most once a minute, and never twice at once.
- **Daniel's own state** (`map-state.json` in the data folder, never the repository): a saved `(x, y)` per part or actor id, a tier per part id, which beats the map's, and the project's view (the camera's pan and zoom).
- **Placement.** A part with no saved position is placed once, near the parts it links to (else the parts of its `zone`), clear of every plate, then saved; a placed part never moves on its own. A plate drags past 6 px of pointer movement, so a click never nudges it, and its place is saved when it is let go.
- **The camera** (#383). The map area never scrolls: it pans and zooms the world. **Panning**: dragging the empty background pans the view, under an open hand that closes while dragging; dragging a part still moves and saves the part. **Zoom**: a wheel, a two-finger scroll or a trackpad pinch (which the browser reports as a wheel with Ctrl held) over the map zooms around the pointer and never scrolls the page, held between 40 % and 200 %. **Fit**: ⌘0, `studio::FitMap` in the palette, puts the whole map in view, centred with a gutter, at no more than 125 %. Each project's view is saved in `map-state.json` beside its positions a moment after it moves, so it survives a restart; a project never moved opens at 100 % with the world's corner at the area's. When a part's sheet opens, the camera pans just enough to show that part whole beside it, once per opening; positions are never written by revealing. A PR brief takes the camera while it plays and gives Daniel's view back, as it found it, when it closes; while it plays, a drag of the background or a zoom does nothing.
- **The left panel** (`ui/panel.ts`, #385). While the view shows, everything Daniel reads beside the map opens in one panel floating over the map's left side, so he never leaves the map to read: a session's story (the story rail itself, moved in; see [The story rail](rail.md)), History, a turn's whole diff, or Settings. Pressing a session's row in the list, or its agent chip on the map, opens its story there, and that session's chips stay lit while it is open; a second press on the same row, or Esc, closes it and selects no session. A Worker's chip, or a subagent's line, opens that subagent's log in the panel (#386); closing it selects no session. History opens there from the list's "History · N" and `studio::ShowHistory`; a turn's diff (the evidence line's "more lines" and "Open full diff", or `studio::OpenFullDiff`) opens there widened to at most 780 px and closes the part's sheet, and its Back shows the story again. Settings opens there from a quiet gear at the top bar's end, or `studio::ShowSettings`. Its width is the rail's. The panel and the part's sheet (and the drawer) share one glass, Treatment C's part sheet, in one class, `glass`: a near-opaque surface, an 18 px backdrop blur, a top highlight, a faint 1 px edge, a deep shadow and a 14 px corner, inset 22 px from the map's edges. Neither darkens the map, which stays lit and clickable; a PR brief alone dims the map, and dims both with it. Each slides in 12 px with a fade on Treatment C's ease, at once under reduced motion. Opening or closing one never moves a part: the map keeps the whole stage and the cards float over it, and when the panel or the sheet would cover the part in focus (the sheet's part, the parts the open session's chips are on) the camera pans just enough, never past what the band between them holds. Below 1007 px only one is open: opening the sheet closes the panel, and the other way round. The Ready for review tray sits at the map's foot on the left and moves right of the panel while it is open.
- **Esc** peels the layers, in order: an overlay (the pre-flight), a drawer, a PR brief (closing it keeps its step), a scrubbed commit (back to now), a part's sheet, the left panel. On the bare map it does nothing: the map is never left.
- **Pre-flight** (`server/src/pre_flight.rs`, `understanding/src/pre_flight.rs`, `ui/map-pre-flight.ts`; #394 of spec #378). Before starting work, Daniel sees which parts it will likely cross. The map's head has a quiet Pre-flight button, and the palette has `studio::PreFlight`; either opens an overlay over the map in the glass, and pressing it again closes it. Its inputs are an open issue (the project's open issues as `gh issue list` gives them), one or two lines of free text, or parts picked by hand. For an issue or text, the server asks the PR briefs' writer, which has no tools (`claude -p`, model `prBriefs.model`), which part ids the work will cross; the issue's title and body go only to that writer, fenced as text to read, never to a background run. Ids not on the map are dropped; a failed call, a reply that does not read or one that names no part on the map shows the hand picker with why. The parts are framed on the map with a dashed outline and the word *predicted* (*picked* for parts picked by hand), and the overlay lists each with its laws on trust, its fog and its staleness band (the map's own, below). Clear takes the pre-flight off the map. One pre-flight is kept per project, in the data folder's `pre-flight-by-project/`, and the Map view's payload carries it (`pre_flight`). When a PR's brief is written and the project's pre-flight is of an issue, the server notes every issue the PR closes (not only the lowest, which the facts still read as the spec) with each one's parent (`gh issue view --json parent`); a brief whose PR closes the pre-flighted issue, or a sub-issue of it, opens with "You expected X, Y; it touched X, Z", where touched is the parts the brief's shape found (those that fog and the ones only mentioned). A pre-flight from free text or hand-picked parts has no issue, so no brief carries its line. The overlay closes with Esc before every other layer, and its field is a text field, so single-key shortcuts do not fire while Daniel types in it. A past commit's map shows no pre-flight.
- **PR briefs** (`server/src/pr_briefs.rs`, `ui/map-brief.ts`; the one doc for them is [PR briefs](pr-briefs.md)). When a lookup finds a PR ready the server writes its brief through `write_pr_brief` (always with `claude -p`, whatever `summaries.writer` says; model: `prBriefs.model` in `settings.json`, Opus by default, read on each write, the writer's and the claim check's alike) and stores it per PR and head under the data folder's `pr-briefs-by-project/`. A new head marks the stored brief stale; it is written again when Daniel opens it, or when two lookups in a row see the same head. Opening a tray row plays the brief as a single story or one chapter. A PR that would fog more than two parts has one tray row per chapter; each chapter opens on its own and resumes at the step left, its frame holds every part its behaviour crosses, the overview (when there is one) plays before the first chapter opened and once per brief, and the "Also touched" lines show on the last step of the last chapter: the light runs the step's links at one speed and parts light as it arrives, the camera frames the parts the brief lights, the panel keeps its tallest step's height and crossfades, a figure (`states`, `sequence`, `compare`) is drawn by code from the writer's labels, citations sit in quiet type, a brief the writer saw only part of the diff for says "Written from part of the diff", and an item the checks left flagged says "not confirmed from the facts". "See the code" opens the PR's changed files, with their diffs, in the drawer above the brief (`pr_diff`; what the step quoted when git cannot give them). Opening a brief returns a scrubbed map to now; closing it with Esc or Leave keeps the step it was at, and finishing it starts it over. Motion respects reduced motion, where the whole step lights at once. A check of kind `pick` is answered in the panel (pick, take it back, Check); an `order` check shows its question until its map answer is built.
- **Ready for review** (`server/src/prs.rs`, `ui/map-tray.ts`). The server asks `gh pr view <branch> --json number,title,isDraft,state,headRefOid,body,closingIssuesReferences` for each listed session's branch: at once when a turn ends, and when the page gains focus or the Map view opens through one cooldown of a minute per repository with an in-flight guard; never on a timer. A PR is ready when it is open and not a draft; its head is kept in memory and replaced by a later lookup. The tray at the map's foot lists the project's ready PRs: a PR whose brief is stored is one row, or one row per chapter of a chaptered brief, that opens it; one being written says "writing the brief…" and waits (the map stays usable); one without a brief opens, and opening writes it in the background, the panel saying "Writing the brief…" until it lands and opens; one whose write failed says so and opens to try again. At start only the ready PRs whose head moved within `briefBackfill.hours` (2 by default; the older `catchUp.hours` is still read) get their brief written or a stale one rewritten, the newest head first and at most 3; a PR that becomes ready while `plotkeeper` runs is written at once; any other is written when opened. Any PR number found still names its session ("PR #N"). A ready PR whose touched parts would not fog at Daniel's effective tiers (Core always, Interface-only when the map's diff names the part, Black box never) gets no brief: the lookup builds its facts, finds no required part, writes nothing, does not gather it again at the same head, and its tray row says "no brief: nothing you track changed".
- **Ratifying** (`server/src/ratify.rs`, `ui/ratify.ts`, `ui/map-ratify.ts`). Daniel accepts or overturns what a PR changed on the map and what its agent decided; it never blocks anything, and the merged map is in effect at once. An item is a map change (a part, outside actor, link, law or flow added, changed or removed, read by code from the map's diff; a part's `tier` and `zone` never count) keyed by (PR, kind, map id), or a decision the agent declared, from the brief's `decisions`, keyed by (PR, decision id). Decision ids come from the writer entry and survive a reworded rewrite; a decided item a rewrite no longer holds keeps its record and is still listed. The state is `ratify.json` in the data folder, per project: when the project's first run was (`since`) and a record per decided item (`accepted`, `overturned`, or `pending`, with the time and what the item said). A reader ignores what it does not know. No record means ratified for anything that landed on or before `since`, and "not yet ratified" for anything after; a `pending` record marks an item not yet ratified whenever it landed, which is how Daniel's own file keeps the laws #295 left open, edited once by hand (no product logic names them). The brief ends with a **Ratify** step listing its items (nothing is added when all are ratified), each with Accept and Overturn; the part sheet marks a law row, and lists a link at the part, "Not yet ratified" with the same two buttons, for a map item that landed after the first run with no record. **Overturn** records the decision and copies a self-contained prompt to the clipboard (the PR number, its branch while the PR is open, the item's id and its wording; `navigator.clipboard.writeText()`), saying "Prompt copied, paste it into your agent"; when the clipboard refuses, the prompt shows in a small box with a Copy button. The note shows only on the sheet or the brief that holds the overturned item. Nothing is typed into a session.
- **Background runs** (`server/src/runner.rs`, `ui/map-runs.ts`; the one doc for them is [Background runs](background-runs.md)). The side area lists the project's runs under the agents no part holds: a running run, the queue behind it, each ended run with how it ended, Cancel or Dismiss, and one indicator with Resume while a login or limit failure pauses the queues.
- **No map.** A project without the file shows a calm empty state, and shows the drafting prompt to give to a session in the project; the page starts no session.
- **Fog** (`server/src/fog.rs`). The first time the view opens a project, the server records the default branch's tip, so every part starts clear. After that it walks the new first-parent commits and files each part's changes in `map-state.json`: **thick** when a law on the part, a link at it (its id or ends), a flow through it or its `paths` changed, or the part was added; **thin** when files it owns changed (placed by the union of the commit's map and its parent's, so a moved file touches both parts) or only its name, caption, purpose or held items (their paths included) did, or the `kind` or `reason` of a link at it; nothing for `zone`, `ignored` or `tier`. A removed part leaves the live map. What shows is by Daniel's effective tier: a Black box part never, an Interface-only part only thick. Strength is never a count. **Reading a brief clears it** (#342): a chapter is complete when its last step was seen (`watchSeen`) and its check was answered, right or wrong, when it holds one; a single story is one chapter over all its lit parts. Once every chapter of a PR's brief that lights a part is complete, that PR's entries leave that part at once and the mist lifts; a part no chapter lights keeps its fog, and leaving mid-chapter clears nothing. Completion is kept as "read at head X" per chapter in `map-state.json` (`fog.reads`). A PR read before it merges files fog at merge only for the parts touched by the diff from X to the squash commit, limited to the paths the squash commit itself changes (so main merged into the branch fogs nothing), at the strength that diff earns; none when nothing was pushed after the read. "I know this" still clears a whole part, and so does reading its [part catch-up](pr-briefs.md#part-catch-ups) to the end, for the entries it covered.
- **Mist.** A fogged plate has a cool-grey mist around it (#455): dense beyond the plate's edges and at its rim, thinning to nothing over its name, caption and marks, so they read at full contrast (4.5:1, measured by snap's contrast pass); the caption is not dimmed. Thin and thick still read apart: thick is denser, with a rim and a slow drift. "I know this" on the part's sheet clears that part's fog and lifts the mist (no motion under reduced motion), and is logged as its own event (Stop rules).
- **The part sheet** (`ui/map-sheet.ts`) opens over the map's top right, in the left panel's glass, on a click that was not a drag (a press on an agent chip opens the chip's session instead): the purpose, then the held items, each its name, its sentence and its key files (its `paths` as written; an item without paths shows none), the tier (Core, Interface-only, Black box; changed in place and kept in `map-state.json`), the laws (backed by a check or on trust), the fog status and, for a fogged part, its [part catch-up](pr-briefs.md#part-catch-ups) (or the one PR brief chapter that lights it) as the main button with "I know this" as the quiet second, or, on a part with no fog, the refresher (below). The first Esc closes it; the next closes the left panel, if open. × (named "Close") closes it too, and so does a click on the empty map (#445): a press on the background that moves 4 px or less between down and up closes the sheet and its drawer, while one that moves further pans and keeps them. A click on another part switches the sheet to that part. The agents not placed, the sheet, the drawer under it and the background runs are one column at most the map's height less its insets, the agents first, so their line keeps the map's top right and an open sheet never pushes it down over a part (#466). The agents not placed are one line of fixed height, "N not placed" (with "· N need you" when any does), and while a sheet is open the line keeps its height even with no agent in it, so agents joining and leaving never move the sheet while the list is closed (#472; in the event log the list changed about every 30 s while agents ran). The column scrolls as one: the sheet and the drawer never scroll on their own (a drawer's code block keeps its own short scroll), and a scroll past its end never moves the map. The sheet is 360 px wide at first; dragging its left edge resizes it between 300 px and half the map, and so do the left and right arrow keys while that edge has the focus. The width is kept in this browser, and a double-click on the edge puts it back to 360 px.
- **Keyboard** (#460). Each plate holds an open button over its name and caption, named by them, beside its agent chips rather than around them. Tab reaches a part's button and then its chips, the parts in the map's reading order (top to bottom, then left to right; a plate within half a plate's height of a row's highest plate reads on that row; `readingOrder` in `ui/map-model.ts`), set when the map draws. Enter or Space opens the part's sheet, as a click does, and the page's focus ring marks the part; in a brief's order question the same press counts as a tap. Actors take no focus, since a click on them does nothing. Plates cannot be moved from the keyboard, nor the camera panned or zoomed: placement is Daniel's own arrangement, and every action the map offers stays reachable without it (#452).
- **Staleness bands** (`server/src/staleness.rs`, `ui/map-stale.ts`, #392). A part whose effective tier is Core carries a mild band along its plate's foot, in the muted text tone and firmer with each band, once Daniel has not engaged with it for 3 weeks (band 1), 6 (band 2) or 12 (band 3); its sheet says "You last engaged with this part 3 weeks or more ago" (6, 12). Interface-only and Black box parts never band; a past commit's map shows none. Staleness is the time since his last entered activity on the part, never since its last commit: a brief chapter read to its end that lights it (read from `fog.reads`, so a chapter read before staleness shipped counts, and kept in `staleness.parts` too as it is read, since a brief rewritten to light its parts differently clears its `fog.reads`), a part catch-up, the refresher, or "I know this". Any of them clears the band at once. A part's baseline is the first time this build showed the project's map (`staleness.since` in `map-state.json`) or, when later, the committer time of the first first-parent commit on the default branch whose `system-map.json` lists the part's id, so nothing is stale on day one and a part added to the map, a split's new parts included, starts with no band; a newer activity beats either. That time is read from git's history of the map file once per project and part while the server runs and is never stored (`staleness::births`, `history::part_births`); the other activities are kept there per part (`staleness.parts`, the last one's time and kind). The bands show on the map and at pre-flight only (`MapState.stale`, the band of each stale part), never anywhere else.
- **The refresher** (#392). A part's sheet with no fog offers **Refresher**: the part as the map has it now, drawn by code from the map file at once, never a writer call. The sheet already shows its caption, purpose, held items and laws with their backing; the refresher adds, under the laws, the flows through the part (each flow's hops on a link at the part, in order) and what it is linked with. Entering it is an activity on the part (`map_refresher`), so its band clears, and is logged (Stop rules).
- **The header's dot.** A project's header in the session list carries one quiet dot, with no count, while a part whose effective tier is Core is fogged, a law is broken (below) or a PR brief is waiting (a ready PR of the project has a stored brief, as `pr_briefs.rs` keeps them; it counts as waiting until the PR is no longer ready); its hover names which. The page asks the server (`map_marks`) when the saved project list changes and when the page gains focus, never on a timer.
- **Live agents.** A session in `Running` or `Needs you` and each of its running Workers show as a chip on every part the current turn touched: the changed files of the turn's trees (a Worker's are the ones its name is on) plus an Edit or Write in flight, placed by `studio-system-map` through `map_place`. A `Needs you` chip keeps the loud `--needs-you` pill. A session with no changed files yet, an agent that reports no turn trees, a status-only one (Codex) or one whose edits are all ignored or owned by no part shows in a quiet **not placed** list beside the map, closed to its one line until a click opens it. Opened, it stays open while agents come and go, and its rows then move the sheet; once it empties it comes back closed. A Helper, a plain shell and a session in `Your turn`, `Idle` or `Ended` are never on the map. Pressing any chip selects its session or Worker and leaves the view. `hideAgents(true)` (`ui/map-agents.ts`) clears every chip and the list, for a view of a past commit.
- **Broken laws** (`server/src/ci_laws.rs`). The server asks `gh` for the latest finished run of `studio.yml` on the default branch when the view opens, when the window gains focus while it is open and when a task is first seen merged, never on a timer, and keeps the answer in memory. While a newer run is going it keeps the last finished one and says so ("for an earlier commit"). When that run failed it fetches the failed log and reads the failing tests of `cargo nextest` (`FAIL [..] binary name`) and of Node's test runner (TAP `not ok`, or the spec reporter's `✖`). A law's test is the function right after its `@law: <id>` tag, read from the run's commit; only a failure of that test marks the owning part: a red dot and rim on its plate, and one line, "A test that backs laws here failed on main", in its sheet and in the header's dot; the law is never named. Another test failing in the same file marks nothing. A missing mark means only "no known failure": a run that failed before the tests ran (fmt, clippy, build) or in untagged tests says "the law tests did not run", one whose log cannot be fetched or holds nothing says so, and a passing run says "passed"; none of these marks a part. The header's dot reads the answer in memory, so a project shows it once its Map view has been opened since Studio started.
- **The drawer** (`ui/map-drawer.ts`) opens read-only under the part sheet and shows blocks of code or text with jumps out of it. "See the proof" on a law a check backs shows the tagged test from its `@law:` line to its closing line, read from the default branch; "See the CI log" on a part that holds a check-backed law or a broken one shows the run's status and the end of its failed log, with "Open on GitHub". Esc closes the drawer before the sheet. `openDrawer(drawer)` takes any `Drawer` (`ui/map-model.ts`), which is how the history strip shows a commit's files.
- **The history strip** (`server/src/history.rs`, `ui/map-history.ts`) sits at the foot of a part's sheet: the first-parent commits on the default branch, from the commit that introduced `system-map.json`, that touched the part (placed by the union of the commit's map and its parent's, or that added or removed it), oldest first, each as `#PR title` when the subject ends `(#N)`, else the subject. A commit Daniel has not caught up on (its fog entries) has a filled dot, an older one a hollow dot. Clicking a commit shows the map as of it, read leniently so a field of another time never breaks it and a deleted part still shows: read-only, with no fog, no broken-law mark, no live agents, no not placed list, and the sheet without tier change, proof, fog or CI. A quiet banner says "Viewing <commit> · Back to now". A commit's "Files" opens its changed files and diffs in the drawer, with "Open on GitHub" when `origin` is on GitHub. A scrub is one call, `scrubTo` (`ui/map-history.ts`), which asks the server's `map_at`.

## Seen

One helper, `watchSeen` (`ui/seen.ts`), decides when something counts as seen: it covers at least half of itself or at least half of the viewport (so a card taller than twice the viewport can be seen) for 500 ms without a break, in a visible and focused window, with the view that holds it open (the Map view). It fires once. The story rail's cards use it, so a card is told as shown when seen and not when it is built; stored `shown` times are not rewritten.

## Stop rules

Studio always keeps a quiet count of what Daniel uses of the map, with no setting and nothing shown (`server/src/stop_rules.rs`, `ui/stop-rules.ts`). The window tells the server, which appends one line per event to `stop-rules.jsonl` in the data folder; a line this build cannot read is skipped, so an older or newer log never breaks it. Events, each with its local calendar day and, bar the first, its project:

- `session`: the session list had a session that day (once a day).
- `map-open`: the Map view opened on the project (once a day).
- `map-action`: an entered action on the map with no event of its own, a part's sheet opened or an agent chip clicked (once a day).
- `scrub`: a commit of a part's history strip was shown (`scrubTo`).
- `proof`: the drawer opened, from "See the proof", the CI log or a commit's files.
- `know`: "I know this" cleared a part's fog. Kept on its own, with no threshold in project 2.
- `refresher-entered`: a part's refresher was entered. `stale-entered`, beside it, when the part had a staleness band; a part catch-up entered from a stale part logs it too.
- `dismissed`: the review of one module was dismissed for the project; the line names the module. An older line with no module, from when dismissal was one flag per project, counts as dismissing the modules of its time (Map view, history strip, See the proof, PR briefs and the skipping note).
- `pre-flight-run`: a pre-flight framed its parts on the map, predicted or picked by hand. An entered action.
- `back-law-started`: a back a law run was started from a law on trust in a part's sheet ([Background runs](background-runs.md#back-a-law)). An entered action.
- The PR brief's events (`brief-offered`, `brief-opened`, `chapter-done`, `check-answered`, `ratify`, `unconfirmed-seen`), each with its PR, and the part catch-up's (`catch-up-offered`, `catch-up-opened`, `catch-up-done`) are in [PR briefs](pr-briefs.md#stop-rules).

An **active day** is a local calendar day with a `session` or `map-open` event. An **engaged day** is an active day with at least one entered action on the project's map: `map-action`, `scrub`, `proof`, `know`, `brief-opened`, `chapter-done`, `check-answered`, `ratify`, `refresher-entered`, `stale-entered`, `catch-up-opened`, `catch-up-done`, `pre-flight-run` or `back-law-started`. A day the map was only open on is not one, and an older log's `mark-seen` lines count for nothing. A project's merged PRs are the first-parent commits on its default branch whose subject ends `(#N)` or starts `Merge pull request #N`, counted since the first event was logged, so the count starts when tracking does. The server hands the window these counts (`stop_facts`) and the window evaluates them (`unused`), only when the Map view opens, never on a timer.

The review is due once a project has **14 active days and 20 merged PRs**, whichever comes last. It lists only the modules below their threshold: the **Map view** (4 engaged days), the **history strip** (scrubbed twice), **See the proof** (the drawer opened twice) and **PR briefs** (opened for a quarter of the merged PRs that had one offered; with a note when "I know this" cleared more fog than finished chapters did), **part catch-ups** (3 read to their end), **Pre-flight** (run twice), the **refresher** (entered twice), **staleness bands** (one refresher or part catch-up entered from a stale part), **explain-back** (3 lines written in the end-of-story bar) and **Back a law** (one run started). A part turns stale 3 weeks after its staleness baseline at the earliest, so the refresher and staleness bands are judged no earlier than 5 calendar weeks after the project's staleness baseline (its first map shown with that build; the facts carry it as `stale_since`) or its first logged day, whichever is later, and not at all before it has a baseline. It is one quiet sentence with a Dismiss button, never a score, a streak or a count. It shows in the Map view's head only. Dismiss dismisses the modules the sentence named, per project and for good, while the log goes on; a module it did not name, or one whose exception ends later, still shows in a later review.

**How a module joins the review.** Each module is one row of `table` in `ui/stop-rules.ts`: its `module` id, its `name` in the sentence (or a `note`, its own sentence, for a note such as skipping), its `kept` bar over the facts the server hands over, and at most one exception before which it is not judged at all: `wait` (a calendar wait of some weeks from `from`, the module's rollout day or a day read from the facts, such as the staleness baseline, or from the project's first logged day when that is later) or `offers` (at least `least` events of one kind logged for the project). A module adds its event kinds to `Kind` in `server/src/stop_rules.rs` and `StopKind` in `ui/types.ts`; the facts carry every kind's count for the project (`counts`), so a bar or an offer count over plain counts needs no new field, and `entered` says whether a kind makes an engaged day. A dismissal is stored with the row's `module` id, so the id never changes once shipped.
