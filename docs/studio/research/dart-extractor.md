# Dart extractor: the rules a text-only `dart-imports` must follow

Research notes for issue #542. They set out how a text-only `dart-imports` extractor turns a Dart repository's directives into `(dependent file, dependency file)` pairs over its tracked files, without running `dart`, `flutter` or `pub` and with no `.dart_tool/package_config.json`. They extend the "Dart" section of `language-extractors.md` and the Go pilot's note, `go-extractor.md`, and don't repeat either. Studio terms follow `docs/studio/CONTEXT.md`. The extractor contract is `docs/studio/behaviour/map.md`, "The extractors", and spec #529 (Problem / Unsure / Pair).

## 1. Directives

- A library is `<scriptTag>? <libraryName>? <importOrExport>* <partDirective>* (<metadata> <topLevelDeclaration>)* <EOF>`. **[cited]** Spec `:19977`. So the script tag comes first, then `library`, then imports and exports in any mix, then parts, then declarations.
- The parser enforces the same order. An import or export after a `part` is an error (`importAfterPart`, `exportAfterPart`). Any directive after a declaration is `directiveAfterDeclaration`. A second `library` is `multipleLibraryDirectives`. **[cited]** `directive_context.dart:28-106`. These are "recoverable" errors: the parser goes on, but the code does not compile. **[cited]** same file, `reportRecoverableError`. So for code that compiles, a reader can stop at the first token that does not start a directive. The SDK has exactly such a mode: `tokenizeDirectives`, "Scan directives and as little as possible after the directives", stops after a `;` that is not followed by `@`, `part`, `library`, `import` or `export`. **[cited]** `abstract_scanner.dart:989-1035`.
- `import`: `<metadata> import <configurableUri> (deferred? as <typeIdentifier>)? <combinator>* ';'`. **[cited]** Spec `:20096`. The parser reads it as the URI, then the conditional URIs, then the prefix, then the combinators. **[cited]** `parser_impl.dart:970-993`. "the grammar enforces that a deferred import includes a prefix clause". **[cited]** Spec `:20134`. A deferred import is still a dependency: the docs import one with `import 'package:greetings/hello.dart' deferred as hello;`. **[cited]** https://dart.dev/language/libraries, "Lazily loading a library".
- `export`: `<metadata> export <configurableUri> <combinator>* ';'`. **[cited]** Spec `:20579`.
- Combinators: `show <identifierList> | hide <identifierList>`. **[cited]** Spec `:20688`. `single-combinators`, "Allow at most one `show` or `hide` combinator per import or export directive", has `enabledIn: '3.15.0'`. That is the next release, not yet stable. **[cited]** `experimental_features.yaml:210-212`. Combinators narrow names, not files, so the extractor skips them. **[judgement]**
- `library`: `'library' qualified? ';'`. **[cited]** `parser_impl.dart:917-940`. The name is optional since 2.19. **[cited]** `experimental_features.yaml`, `unnamed-libraries`. It names no file. **[judgement]**
- `part`: `<metadata> part <uri> ';'`. Its target "must be a valid part declaration", compiled "in the scope of the current library". **[cited]** Spec `:20887`, `:20915-20919`. Two `part` directives with one URI are an error (`:20923`), and so is one part used by two reachable libraries (`:20926-20945`). Part URIs take no conditions (`parser_impl.dart:1321-1329`).
- `part of`: `<metadata> part of (<dottedIdentifierList> | <uri>) ';'`. **[cited]** Spec `:20889`; `parser_impl.dart:1331-1355`. It must be the first directive, and a part may hold no other directive (`nonPartOfDirectiveInPart`) unless the experiment below is on. **[cited]** `directive_context.dart:108-119`. The name form is discouraged. "DO use strings in `part of` directives", lint `use_string_in_part_of_directives`. **[cited]** https://dart.dev/effective-dart/usage `:26`. So today a part file holds no imports. Every dependency of its code is declared by its library file. **[judgement]**, from the grammar.
- Doc imports: `/// @docImport 'uri';` inside a doc comment is read by the analyzer for doc links only. **[cited]** `uri_with_interpolation_test.dart` (`test_library_docImport`), `analysis/file_state.dart:983`. It is a comment, so a reader that skips comments drops it. That is right, since it is no build dependency. **[judgement]** Measured: 214 files in flutter/packages, 9 in dart-lang/core. **[measured]**
- `dart-ext:` URIs are an error (`useOfNativeExtension`). **[cited]** `library_analyzer.dart:964-965`.

### Not shipped: enhanced parts, augmentations, unquoted imports

All of these appear in `experimental_features.yaml` with no `enabledIn`, so all are off in every release. **[cited]** `:138-155`.

- **Enhanced parts** (`enhanced-parts`, `experimentalReleaseVersion: '3.6.0'`; spec "Status: Accepted"). Part files gain `import`, `export` and nested `part` directives. `<partDeclaration> ::= <partHeader> <importOrExport>* <partDirective>* …`. `part of` must take a URI: "**Breaking**: A `part of` file directive cannot use a library name any more." Part URIs stay unconditional: "It was previously specified that `part` directives could use configurable URIs. This has been removed". **[cited]** `parts-with-imports/feature-specification.md:101-200`, `:720-744`. The parser already has the switch (`isEnhancedPartsFeatureEnabled`). **[cited]** `directive_context.dart:12`, `:44`.
- **Augmentations** (`experimentalReleaseVersion: '3.6.0'`). `import augment` and augmentation libraries came from earlier drafts. Version 1.22 says "Unify augmentation libraries and parts", so augmentations now live in part files. **[cited]** `working/augmentations/feature-specification.md:1870-1875`, `:1917-1919`. The parser still reads `augment library 'uri';` behind the flag. **[cited]** `parser_impl.dart:899-915`.
- **Unquoted imports** (spec "Status: Accepted", no release version). `uri ::= stringLiteral | packagePath`, so `import test;` means `package:test/test.dart`, `import a/b/c;` means `package:a/b/c.dart`, and `import dart/async;` means `dart:async`. `part` and `part of` stay quoted. **[cited]** `unquoted-imports/feature-specification.md:412-527`.

**What this means.** A reader written today meets none of these in compiling code. Two choices make it ready for them at no cost. It can keep reading directives after `part of`, which current code never holds. And it can treat an `import` or `export` followed by an identifier as a directive it cannot read, never as the end of the header. **[judgement]**

## 2. URI resolution

- The spec says: "A URI of the form `dart:s` is interpreted as a reference to a system library". "A URI of the form `package:s` is interpreted in an implementation specific manner." "Otherwise, any relative URI is interpreted as relative to the location of the current library. All further interpretation of URIs is implementation dependent." **[cited]** Spec `:21091-21107`. A part's `part of` URI is resolved "against the URI *U*" of the part itself. **[cited]** `parts-with-imports/feature-specification.md:196-199`.
- `import ''` resolves to the file itself. dart-lang/tools' generated `pkgs/boring/lib/src/bindings/boringssl.g.dart:23` has `import '' as self;`. **[measured]** The core already drops self-pairs. **[repo]** spec #529, "The core enforces the contract".
- **`package:` maps to `lib/`.** `package_config.json` gives each package a `rootUri` and an optional `packageUri`, "the directory containing files available to Dart programs using `package:packageName/...` URIs". **[cited]** `package-config-file-v2.md:65-66`. Pub always writes `packageUri: 'lib/'`, both for dependencies and for every workspace package. **[cited]** `entrypoint.dart:505-531`, and `:1004`: "Pub always makes a packageUri of lib/". The docs agree: `import 'package:enchilada/some/path/olives.dart'` is `lib/some/path/olives.dart`. **[cited]** https://dart.dev/tools/pub/package-layout `:214-262`.
- **The name is the pubspec's `name`.** A path dependency's pubspec is loaded with `expectedName: ref.name`, and pub throws if the names differ. **[cited]** `source/path.dart:229`, `pubspec.dart:273-274`. "Every package needs a name". It is `[a-z0-9_]` and "a valid Dart identifier". **[cited]** https://dart.dev/tools/pub/pubspec `:153-158`. The docs' workspace root is named `_`. **[cited]** https://dart.dev/tools/pub/workspaces, first example. Every tracked pubspec in the five repositories has a `name:` line. **[measured]**
- **`package_config.json` is never tracked.** It is written by `dart pub get`, and `.dart_tool/` "should never be checked into source control". **[cited]** https://dart.dev/tools/pub/package-layout `:646-656`. None is tracked in the five repositories. **[measured]**
- **Nested packages.** "a file belongs only to the package with the nearest package root". "It is an error if the package URI of a package is inside a nested package's root URI." **[cited]** `package-config-file-v2.md:70-77`. No tracked pubspec sits under another package's `lib/` in the five repositories. 101 sit under `example/` in flutter/packages, and 10 under `test/` in dart-lang/tools. **[measured]**
- **Workspaces** (Dart 3.6). The root pubspec lists members under `workspace:`, globs allowed since 3.11. Each member has `resolution: workspace`. Workspaces can nest. One `package_config.json` sits at the root. **[cited]** https://dart.dev/tools/pub/workspaces `:50-160`. "Workspace members must have unique names" is a hard failure. **[cited]** `package.dart:519-528`. Members "will automatically resolve to the one in the workspace, regardless of the source". Outside the workspace "the original source (here implicitly `hosted`) is used". **[cited]** workspaces `:232-249`.
- **A local package is not always the one used.** Without a workspace, a path dependency or an override, a dependency on a package the repository also holds resolves to the pub.dev copy. **[cited]** workspaces `:232-249`, https://dart.dev/tools/pub/dependencies, "Path packages". Measured, dependency entries naming a package the repository holds, by how they are declared: flutter/packages has 485 hosted (386 of them under `dependencies`) and 46 `path:`. dart-lang/tools has 58 hosted, 13 `path:` and 2 workspace. riverpod has 76 workspace and 2 `path:`. bloc has 87 hosted and 14 `path:`, plus 28 tracked `pubspec_overrides.yaml` files. **[measured]**
- **Relative imports across `lib/`.** "a relative import path in a file inside `lib` can't reach out and access a file outside of the `lib` directory, and a library outside of `lib` can't use a relative path to reach into the `lib` directory." `package:my_package/api.dart` and `../lib/api.dart` are "two completely unrelated libraries". **[cited]** https://dart.dev/effective-dart/usage `:83-130`. Both name the same tracked file, so for a file-level pair they are one target. **[judgement]** Measured: 1 import in flutter/packages escapes `lib/`, to a file that is not tracked. **[measured]**
- `dart:` names SDK libraries and never a tracked file. Flutter's `sdk: flutter` packages and the old synthetic `package:flutter_gen` have no tracked pubspec in an ordinary repository. The tool "will no longer generate a synthetic `package:flutter_gen`". **[cited]** https://docs.flutter.dev/release/breaking-changes/flutter-generate-i10n-source, "Summary". Other schemes and absolute paths are "implementation dependent" (Spec `:21106`) and name no tracked path. **[judgement]** None was seen. **[measured]**

## 3. Conditional imports and exports

- `<configurableUri> ::= <uri> <configurationUri>*`, `<configurationUri> ::= if '(' <uriTest> ')' <uri>`, and `<uriTest> ::= <dottedIdentifierList> ('==' <stringLiteral>)?`. **[cited]** Spec `:21015-21021`; `parser_impl.dart:1110-1170`. A test with no `==` "is equivalent to `ids == "true"`". The tests are tried "in source order", and the first match wins. Otherwise the first URI is used. **[cited]** Spec `:21029-21075`.
- "Any sequence of dot-separated identifiers is valid syntax. Currently, only keys of the form `dart.library.name` are provided." The docs' example exports `src/hw_none.dart` `if (dart.library.io) 'src/hw_io.dart' if (dart.library.js_interop) 'src/hw_web.dart'`. **[cited]** https://dart.dev/tools/pub/create-packages `:157-195`.
- Conditions apply to `import` and `export` only, never to `part` (§1).
- Measured conditional directives: 27 in flutter/packages (one with two conditions), 3 in dart-lang/core, 2 in dart-lang/tools, 1 in bloc, 0 in riverpod. No `==` form was seen. **[measured]**

**What this means.** The reader takes the first URI and every `if (…)` URI. Each one is a file some platform's build uses. Pairing all of them over-counts for any one platform, but no pair is false. **[judgement]**

## 4. Lexing traps

- **Comments nest.** `<MULTI_LINE_COMMENT> ::= '/*' (<MULTI_LINE_COMMENT> | ~'*/')* '*/'`, "Comments may nest". **[cited]** Spec `:23653-23668`; the scanner counts `nesting` (`abstract_scanner.dart:1964-2016`). Doc comments are `///` and `/** */`, which are ordinary comments to the reader. Measured: no nested comment before the directives in 7,851 files. **[measured]**
- **Strings.** Single and triple quotes, `'` and `"`, raw `r'…'` / `r"""…"""` with no escapes and no interpolation, `$id` and `${expression}`. "the expression inside the interpolation could itself include strings, which could again be interpolated recursively". **[cited]** Spec `:9405-9600`, `:9725-9760`. The scanner rescans the expression inside `${…}` with its full switch, so strings, braces and comments nest. **[cited]** `abstract_scanner.dart:2248-2280`.
- **URI strings.** "It is a compile-time error if a string literal that describes a URI or a string literal that is used in a `uriTest` contains a string interpolation." **[cited]** Spec `:21023-21027`; `library_analyzer.dart:735` (`uriWithInterpolation`). But `<uri> ::= <stringLiteral>` and `<stringLiteral> ::= (<multilineString> | <singleLineString>)+`, so adjacent literals are legal: `import 'a/' 'b.dart';`. **[cited]** Spec `:9405`, `:21015`. The parser collects adjacent strings in a URI (`parser_impl.dart:9237-9254`), and the analyzer joins their values (`ast.dart:196-201`, `:55816-55824`). **[cited]** I did not compile such an import. **Unverified** end to end, high confidence. Raw URIs (`import r'x.dart';`) are legal too. Measured: no adjacent, raw or escaped URI was seen. **[measured]**
- **Before the directives** come only the script tag, comments, and metadata, `@name`, `@a.b` or `@C(args)`. Strings can appear there only inside metadata arguments, so the reader must lex strings, with interpolation, wherever metadata sits. **[judgement]**, from Spec `:19977`.
- **Script tag.** "The script tag must appear before any whitespace or comments". **[cited]** Spec `:20047`. The scanner takes `#!` only at offset 0. **[cited]** `abstract_scanner.dart:1278-1295`. Measured: 3 files. **[measured]**
- **BOM.** The UTF-8 scanner skips a leading `EF BB BF`. **[cited]** `utf8_bytes_scanner.dart:103-107`. Measured: none. **[measured]**

## 5. Test files

- package:test: with no path, "the runner defaults to running tests under the `test/` directory", searching it "recursively" for "`*_test.dart`". "Directories other than `test/` are ignored by `dart test` unless passed explicitly". **[cited]** `pkgs/test/README.md:138-147`. Both are settings in `dart_test.yaml`: `paths` "defaults to `[test]`", `filename` "defaults to `"*_test.dart"`". **[cited]** `doc/configuration.md:304-332`.
- Pub: "the convention is that most of these go in a `test` directory (or some directory inside it if you like) and have `_test` at the end of their file names". Flutter's integration tests "live in their own `integration_test` directory", and "by default `dart test` will not run these tests". **[cited]** https://dart.dev/tools/pub/package-layout `:443-464`.
- Flutter: `flutter test` with no arguments searches only `test/`, "so that files with names like "hit_test.dart" don't get run". **[cited]** `flutter_tools/lib/src/commands/test.dart:441-443`, `:52-54`. `packages/flutter/lib/src/gestures/hit_test.dart` is a production library. **[cited]** `gh api repos/flutter/flutter/contents/…`. Integration tests go in `integration_test/`, with a driver in `test_driver/integration_test.dart`, a name without `_test.dart`. **[cited]** `packages/integration_test/README.md:21-23`, `:40-42`.
- So `test/` is a runner default, and `*_test.dart` is only a pattern *inside* a test folder. Neither is enforced by the language or pub. **[judgement]**
- Measured: helpers under a test folder that don't end in `_test.dart` are 15 files in dart-lang/core, 61 in dart-lang/tools, 74 in bloc, 306 in riverpod and 189 in flutter/packages. Files ending in `_test.dart` outside `test/`, `integration_test/` and `test_driver/` are 0, 0, 2, 4 and 5. bloc's 2 are the production library `packages/bloc_test/lib/bloc_test.dart` and `lib/src/bloc_test.dart`. riverpod's 4 are website snippets. **[measured]**

## 6. Generated files and other count traps

- source_gen writes `.g.dart` files "which are referenced as a `part` in the original source file" through `SharedPartBuilder`. Other builders write their own `.some_name.dart` part extension, or a standalone library to import (`LibraryBuilder`). The combined file starts `// GENERATED CODE - DO NOT MODIFY BY HAND`. **[cited]** `source_gen/README.md:56-79`, `:104-105`. freezed uses `part 'my_file.freezed.dart';`. **[cited]** freezed `README.md:145`.
- Generated files may be tracked or not. riverpod tracks 193 `*.g.dart`/`*.freezed.dart` files, flutter/packages 150, dart-lang/tools 23 and bloc 10. 36 `part` directives in riverpod's lint test fixtures name `.g.dart` files that are not tracked. **[measured]** An untracked target gives no pair, since the core drops it. **[repo]** spec #529, "The core enforces the contract".
- A part shares its library's imports, so a part file in another folder or part has no pairs of its own today (§1). Its code's dependencies show up as the library file's pairs. **[judgement]**
- Duplicate names: dart-lang/core has 1 (`example`), bloc 2, flutter/packages 11, and dart-lang/tools and riverpod 0. All but one are example apps, which only their own tests import. bloc's `authentication_repository` is declared under two example apps. 12 non-test files import it, and each app names its own copy with `path: packages/authentication_repository`. **[measured]**
- Legacy `part of name;`: 16 files in flutter/packages (`packages/material_ui/…`), none elsewhere. **[measured]**
- Templates that are not Dart: bloc's `bricks/**/__brick__/` files hold `{{…}}` mustache. **[measured]** Their imports name no tracked file. **[judgement]**

## What this means for the extractor

Rules, all **[judgement]** built on the citations above:

1. **Package index.** Read every tracked `pubspec.yaml`'s top-level `name:`, bare or quoted, with `#` comments cut. Its folder is the package root, and `package:<name>/<path>` names `<root>/lib/<path>`. A pubspec with no readable `name` is a problem: pub requires one, and the contract wants a Problem for a malformed config (`system-map/src/extract/contract.rs`, `Fixture.malformed_config`). **[repo]** `workspace:`, `resolution:` and the dependency lists are not needed to map a name.
2. **A name declared twice** is Unsure, with every declarer's target as a candidate. This is `Names<T>` as in Go.
3. **Resolution.** For a relative URI, join it to the importing file's folder and normalise it. The empty URI is the file itself. For `package:n/p`, look the name up in the index. `dart:`, `dart-ext:`, other schemes, absolute paths and unknown package names give no pair. A target that is not tracked gives no pair.
4. **Which directives make pairs.** `import` and `export` make an ordinary pair to every URI they name, conditional ones included. `part` makes a pair from the library to the part, flagged `declaration` as `rust-modules` flags a crate root's `mod` (`system-map/src/extract/mod.rs:156`). **[repo]** `part of` makes no pair. It is the back-reference, and its name form names no file.
5. **The reader.** Skip a BOM, then a `#!` line at offset 0. Skip whitespace and comments, nested `/* */` included. Read metadata (`@` and a dotted name, then a balanced `(…)` with strings lexed in full). Then read directives until the first token that starts none. A URI is one or more adjacent string literals, raw or not. One with `$` interpolation is a compile error and is skipped. Keep reading after `part of`, ready for enhanced parts. Count `import`/`export` followed by an identifier (unquoted imports) as unreadable, never as the end of the header.
6. **Tests.** A file is a test when a folder in its path is named `test`, `integration_test` or `test_driver`. The `_test.dart` suffix alone never makes a test.
7. **Detection.** The default rule: a tracked, non-ignored `.dart` file that is not a test.

Stated counts:

- **Over-counts.** Every branch of a conditional import or export. A `package:` import of a local package that the importer's build takes from pub.dev, because there is no workspace, path or override: the pair names the local copy of the same package. Unused imports, as in every extractor.
- **Under-counts.** A part file's own use of its library's imports, which is counted on the library file. Imports from test files. `package:` names no tracked pubspec declares (`flutter`, `flutter_gen`). Unquoted imports, until they ship. Generated targets that are not tracked.
- **Unsure.** A `package:` name two tracked pubspecs declare.
- **Exact.** Relative and `package:` URIs to a tracked file of a package declared once: the pair names the file the compiler would read, given the local copy is the one used.

## Against the starting points

- *"`import`, `export`, `part` and `part of` with relative URIs resolve from the file"*: right for all four (Spec `:21104`; parts-with-imports `:196-199`). Refined: `part of` should make no pair. A part points back at its library, which already pairs with it through `part`, and a part→library pair would be a reverse edge. The empty URI is a self-import.
- *"`package:name/x.dart` resolves to `lib/x.dart` of the tracked `pubspec.yaml` named `name`; a duplicated name is Unsure"*: right. Pub always maps to `lib/` and checks the name (§2). Refined twice. First, a hosted dependency on a local package compiles against pub.dev's copy, a stated over-count: 485 such entries in flutter/packages. Second, most doubled names are example apps imported only by tests. bloc's one real case is settled by the importer's own `path:` dependency, if the grill wants a tie-break.
- *"conditional imports count every file they name (an over-count)"*: right, for `import` and `export`. `part` can't be conditional. The `==` form exists but was not seen.
- *"`dart:` and undeclared packages never resolve"*: right, if "undeclared" means no tracked pubspec has that name. Resolution needs no importer-side dependency list (§2). `dart-ext:` is an error, and other schemes name nothing tracked.
- *"the lexer handles nested block comments, raw strings and `${…}` inside strings"*: right, all three are in the language (§4). Refined: only metadata and URIs carry strings before the reader stops. URIs can't interpolate but may be adjacent or raw literals. The script tag and BOM are the other header traps.
- *"tests: `test/` and `*_test.dart`"*: **contradicted** as an either-or. `*_test.dart` outside a test folder is not a test to `dart test` or `flutter test`, and bloc's `lib/bloc_test.dart` and Flutter's `lib/src/gestures/hit_test.dart` are production libraries. As a both-and rule it misses 15 to 306 helper files per repository under `test/`. The folder alone is the rule (§5), and it should add `integration_test/` and `test_driver/`.

## Open questions for the grill

1. **Test folders.** Is a `test`, `integration_test` or `test_driver` folder at any depth a test folder, or only at a package's root? Are `example/`, `benchmark/` and `tool/` production? flutter/packages has 101 example packages.
2. **Doubled names.** Always Unsure, or break ties as Go does with `go.work`: by the importer's own package, its pubspec's `path:` dependencies or `dependency_overrides`, or workspace membership?
3. **Hosted dependencies on local packages.** Pair them with the local copy (the stated over-count), or pair only with evidence the local copy is used: a workspace, a `path:` dependency or an override? The second needs YAML dependency parsing, and in flutter/packages it would drop most cross-plugin pairs.
4. **`part`.** A declaration pair from library to part, with no pair for `part of`? Should a part file's code count toward its own part through the library's imports?
5. **Unshipped syntax.** Unquoted imports and enhanced parts are accepted but off. Support them now (the mapping is four rules), or wait and treat them as unreadable?
6. **Generated files.** Leave tracked `*.g.dart` and `*.freezed.dart` to the map's `ignored`, or skip them in the extractor?
7. **The trial repository.** riverpod first and bloc second, or flutter/packages for scale?

## After the grill

The grill of 2026-11-26 (`local-evidence/2026-11-26-dart-extractor-grilling/reports/decisions.md`, on Daniel's machine) settled the open questions above:

1. **Test folders:** a folder named `test`, `integration_test` or `test_driver` at any depth, as rule 6 says. `example/`, `benchmark/` and `tool/` are production unless the map ignores them.
2. **Doubled names:** rule 2 gains *own package first*. When the importer's own package (its nearest tracked pubspec) is one of the declarers, the name resolves there, as Go's own module does. Otherwise it is Unsure. There is no `path:` tie-break, since the dependency lists stay unread.
3. **Hosted dependencies on local packages:** paired by name with the local copy, the stated over-count.
4. **`part`:** rule 4 as written. A part file's own use of its library's imports is a stated under-count.
5. **Unshipped syntax:** not supported. Rule 5's readiness stays: `part of` does not end the header, and `import`/`export` followed by an identifier gives no pair and reading goes on.
6. **Generated files:** no special rule. A map author ignores them.
7. **Trials:** riverpod first, bloc second, both required.

Also settled: rule 1's index follows the map's `ignored`, as Java's type index does and Go's module index does not. No tracked pubspec means the extractor falls back cleanly: relative URIs still resolve. A file the reader cannot lex gives no pairs and is skipped, as in Java.
