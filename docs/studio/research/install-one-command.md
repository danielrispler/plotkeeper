# Installing and starting plotkeeper with one command

> **Answer:** Yes, `npx plotkeeper` can be the one command. The npm package already holds native binaries. Hooks point at copies in the data folder, not at the package, so the npx cache's path never reaches a hook. The closest prior art, pixel-agents, does the same thing: it copies its hook script out of the package, asks consent once, and installs again on every consented start. The change from spec #320 is small. The bare `plotkeeper` start runs `install`'s wiring when nothing is wired yet, after one printed summary and a yes. On later starts it rewires only when the plugin plotkeeper renders has changed. `install` and `uninstall` stay as explicit verbs. `npm i -g plotkeeper` stays as the second way in.
> **Evidence:** Strong for the npm, npx and pixel-agents facts: each was read in source at a pinned commit, or in registry metadata on 24 November 2026. Strong that npm-delivered binaries carry no quarantine attribute and that Rust binaries are ad-hoc signed: both were checked on this Mac. **Unverified:** the size of the universal tarball (estimated from the arm64 build), whether `lipo` keeps each slice's signature, how long `claude plugin` takes, and how npx behaves offline.

Research for Daniel's ask of 24 November 2026: installing and running plotkeeper should be "safe, simple, fast and easy, ideally ONE command like `npx pixel-agents`." Spec #320 ("Install and distribution") settled three steps: `npm i -g plotkeeper`, `plotkeeper install`, `plotkeeper`. This note checks that against what similar tools ship. Terms follow `docs/studio/CONTEXT.md`.

## 2. pixel-agents in detail: the model to copy

pixel-agents is the only project here that does what plotkeeper needs: one npx command that wires an agent's hooks and serves a local page. How it does it (`pixel-agents-hq/pixel-agents` at `4dd14d6`, paths under `server/src/`):

- **Hooks run a copy outside the package.** `copyBundledScript` copies `dist/hooks/<name>` from the package to `~/.pixel-agents/hooks/<name>`, with mode 0700 (`providers/hook/claude/bundledScripts.ts:15-37`). The hook command is `node "<that path>"` (`providers/hook/claude/claudeHookEntries.ts:102-105`). So the npx cache can move or be cleaned without breaking a hook. The hook does need a `node` on the agent's PATH, which plotkeeper's native hook does not (my inference).
- **Consent once, in the page.** The disclosure has three facts, kept as single strings so no surface drifts from them (`providers/hook/claude/consentCopy.ts:23-43`): what is written and where, with a one-time backup; what data moves (tool names and inputs) and that it stays on 127.0.0.1 unless `--host`; and how to undo it ("Settings → Instant Detection (Hooks)"). The request is sent only when hooks are not installed, consent is not yet answered, hooks are enabled and the client holds the token (`providers/hook/consentGate.ts:35-44`). A headless start runs without hooks and prints "open the URL below to review and approve it" (`cli.ts`, about :466-470).
- **Idempotent install on every consented start.** "The install path is idempotent and runs on every consented startup, so a partial install repairs itself" (`providers/hook/claude/claudeHookInstaller.ts:99-101`). `cli.ts` (about :451-476) copies the script and calls `installHooks` on each start once consent is `granted`. This is also how upgrades reach the hook: a new version's start recopies the script.
- **Silent migration only when it narrows scope.** A user whose hooks a pre-consent version installed is granted consent without being asked, because "it only ever REDUCES scope" (`cli.ts`, about :456-465).
- **It edits `~/.claude/settings.json` directly**, through a guarded read-modify-write that refuses malformed files (`claudeHookInstaller.ts:16-29`, :143-150). plotkeeper may not do that: see section 4.

## 3. npx, npm and macOS facts that decide the design

- **Where npx puts a package.** If a package is not in the local project, npx installs it "to a folder in the npm cache, which is added to the PATH" ([npx docs](https://docs.npmjs.com/cli/v11/commands/npx)). The folder is `npxCache/<first 16 hex of sha512 of the spec strings>` (`libnpmexec:246-262`). So `npx plotkeeper` always reuses one folder, while `npx plotkeeper@0.3.0` gets a different one.
- **`npx plotkeeper` follows the latest version without `@latest`.** For a name-only spec in the npx tree, npx fetches the manifest with `preferOnline: true` and reinstalls when the resolved tarball differs from the cached one (`libnpmexec:26-37`, :41-45, :72-83, and the comment "If looking in the npx cache check if a newer version is available"). Each run makes one registry request. **Unverified:** what happens offline. The pacote/`preferOnline` fallback to the cache was not read.
- **npx asks before installing, and asks again on an upgrade.** When anything must be added it prompts "Need to install the following packages: … Ok to proceed?", defaulting to yes. Without a TTY, or in CI, it only warns (`libnpmexec:296-316`). An upgrade puts the new version in that list (:282-287), so the user sees npm's own prompt on the first run and on each new version (my reading of the code; not observed).
- **The bin may be a native file.** npx runs the package's single `bin` (docs, "bin selection"). esbuild's `bin/esbuild` and plotkeeper's `npm/package.json` (`"bin": {"plotkeeper": "bin/plotkeeper"}`) both name a native file.
- **`current_exe` resolves into the npx folder.** `beside()` canonicalises `current_exe` (`server/src/bin/plotkeeper.rs`, `fn beside`), so under npx the hook binaries are found in `…/_npx/<hash>/node_modules/plotkeeper/bin/`, and `refresh_hook_copies` copies them into the data folder's `bin/` on every start. (Inference: npm links `.bin/plotkeeper` to `bin/plotkeeper` by symlink. Canonicalisation was read in the code but not tried under npx.)
- **No quarantine on npm-delivered files.** Files that npm downloaded and `tar` extracted carry `com.apple.provenance` and no `com.apple.quarantine` (`xattr -l` on the unpacked vibe-kanban, ccusage and esbuild files, this Mac, Darwin 27.2). Apple describes Gatekeeper's first-run approval as applying to software a user "downloads and opens … from outside the App Store", and its notarization page ties the check to software "downloaded from the internet or transferred with AirDrop" ([platform security guide](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web); [notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)). Verified: an `npm pack` plus `tar` path sets no quarantine. Inference, high confidence: `npm install`/npx extraction behaves the same, since it is the same npm process with no browser involved.
- **Apple silicon requires a signature, and ad-hoc is enough.** "The operating system enforces that any executable must be signed … a simple ad-hoc signature is sufficient," and toolchains "automatically apply ad-hoc signatures at link time" ([Big Sur 11.0.1 universal apps notes](https://developer.apple.com/documentation/macos-release-notes/macos-big-sur-11_0_1-universal-apps-release-notes)). Checked here: plotkeeper's own `target/release/plotkeeper` and `plotkeeper-hook` are `flags=0x20002(adhoc,linker-signed)`, and so is esbuild's npm-shipped `bin/esbuild` (`codesign -dv`). Not checked: that `lipo -create` in `scripts/npm/pack.sh` keeps each slice's signature. No x86_64 build was present. A CI step `codesign -v` on each slice would settle it.
- **Size.** arm64 release binaries here: `plotkeeper` 12.8 MB, `plotkeeper-hook` 0.92 MB, `plotkeeper-answer` 0.72 MB, `plotkeeper-run` 0.85 MB, 15.3 MB in all. A universal build roughly doubles that to about 31 MB unpacked. `gzip -9` shrinks `plotkeeper` to 36%, so the tarball should be about 11 MB (estimate; the x86_64 slices were not built). For scale, on this network: pixel-agents' tarball (1.2 MB) took 0.12 s, ccmanager's darwin-arm64 (42.7 MB) 3.1 s, and Codex's darwin-arm64 (160 MB) 5.4 s. So about 1 s for plotkeeper, without npm's own overhead (one sample each).
- **Install scripts are not needed.** plotkeeper's `npm/package.json` has no `scripts`, and spec #320 already keeps hook upgrades off npm's install scripts ("which may be off"). Codex and ccusage also ship without `postinstall`. esbuild keeps one only as a fallback. CloudCLI's `postinstall` is the counterexample.

## 4. Recommendation, as decided

The proposal this note made was taken, with changes, in [#320's one-command decision](https://github.com/danielrispler/plotkeeper/issues/320#issuecomment-7131528867) and spec #434. This section gives what was decided; the facts above are unchanged.

**`npx plotkeeper` is the one command.** Hooks already point at the data folder's copies (`server/src/install.rs:312-330` at `b8c098530` copies them, and `hook_copies::refresh` keeps them current on each start, `server/src/bin/plotkeeper.rs`, `refresh_hook_copies`). So nothing a harness runs ever names the npx cache, and the cache's hash folder, a cache clean or a Node change cannot break a hook. The server already opens the browser on its token URL (`plotkeeper.rs`, `show`, unless `PLOTKEEPER_NO_BROWSER`).

### The start

1. `npx plotkeeper`. npm asks "Need to install … plotkeeper@x.y.z. Ok to proceed?" and downloads about 11 MB.
2. **Consent in the terminal, not the page.** The server's first instance, after it takes the data folder's lock and refreshes the hook copies, prints one line per harness found in the words `install` prints, the harnesses skipped, where the hook binaries go, that events stay on this machine and that `plotkeeper uninstall` undoes it. Then it asks `Wire these? [Y/n]`, yes by default. It wires on yes and serves either way. The page has no consent screen; it only says "not recording: run `plotkeeper install`" when nothing is wired (#437).
3. **Answers per harness.** Install's record keeps each harness as wired or declined. A start asks only about found harnesses with no answer, so a decline is remembered and a harness installed later is asked about on its own. A second start, one that finds a server running, never asks.
4. **No terminal.** When stdin is not a terminal, the start never asks, never wires and stores no answer. It prints `plotkeeper install --yes` and serves, as npx itself only warns without a TTY.
5. **Later starts** compare a fingerprint per wired harness, a hash of what install rendered for it, with what it would render now (#438). Equal: that harness's CLI is not run. Different, for a wired harness: it is rewired without asking, since its scope did not grow (pixel-agents' rule, section 2). Declined harnesses are never rewired. A rewire of Codex says that `/hooks` must trust the changed hooks once: Codex re-asks trust when a handler's command, args, timeout, async flag or matcher change ([openai/codex@a0d5b0a6, `discovery.rs:1011-1055`](https://github.com/openai/codex/blob/a0d5b0a6/codex-rs/hooks/src/discovery.rs#L1011-L1055)). That settles this note's first open point.
6. **The verbs stay.** `plotkeeper install` wires every harness found, declined ones included, and records each as wired; `--yes` is the same, for scripts. `plotkeeper uninstall` undoes it as before and forgets every answer, so the next start asks again.
7. `npm i -g plotkeeper` and then `plotkeeper` follows the same flow, for a fixed version on the PATH. `npx plotkeeper@0.3.0` pins a version.

### What else was decided

- **No stale entries.** Install's edit of Codex's and Cursor's hook files first removes plotkeeper's entries, those whose command names the data folder's `bin/`, then adds the current ones, so a rewire never leaves two sets (#435).
- **Versions.** The running file also holds the server's version. A second start of another version says which one is running and to stop it and start again, opens the page, and never stops the running server (#439).
- **Publishing.** The first publish is by hand, with 2FA, of the tarball the release workflow's smoke job tested: npm trusted publishing cannot create a package. Later releases use trusted publishing with provenance and no token, and the package script checks `codesign -v -a arm64` on each universal binary; the x86_64 slice is unsigned by design.
- **Docs.** The README leads with `npx plotkeeper`, gives `npm i -g` second, and warns that offline `npx` waits about 70 seconds before it runs the cached copy (#373).
- **Unchanged:** the credentials rule. Claude Code is wired only through `claude plugin`, and plotkeeper never opens `~/.claude/settings.json` (`install.rs:11-16`). pixel-agents' direct edit of that file is the part not to copy. Also unchanged: the data-folder `bin/` copies, macOS only, and no `postinstall`.

### Still open

- Package size: one universal tarball (about 11 MB, estimated) against per-arch `optionalDependencies`. Measure it once `pack.sh` has run.
- Background runs an old server starts after an npx upgrade use the newer package's `plotkeeper-run`. A run already going survives the upgrade, since npm renames the old folder aside rather than overwriting it; beyond the version notice this is not guarded.
